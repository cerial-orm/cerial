A schema can be written as plain TypeScript. You declare models, objects, tuples, enums and literals with factory functions from `cerial/schema`, export them, and `cerial generate` produces the same client it produces from `.cerial` files. The two forms describe the same schema language: every construct has a `.cerial` spelling and a TypeScript spelling, and each page in this section shows them side by side.

## A first schema

```cerial
model User {
  id Record @id
  email Email @unique
  name String
  age Int?
  posts Relation[] @model(Post)
}

model Post {
  id Record @id
  title String
  authorId Record
  author Relation @field(authorId) @model(User)
}
```

```typescript
import { f, model } from 'cerial/schema';

export const User = model('User', {
  id: f.record().id(),
  email: f.email().unique(),
  name: f.string(),
  age: f.int().optional(),
  posts: f.reverse(() => Post).array(),
});

export const Post = model('Post', {
  id: f.record().id(),
  title: f.string(),
  author: f.relation(() => User),
});
```

`Post` has no `authorId` field in the TypeScript form. The relation derives it. See [Relations](/schema/typescript/relations).

## What `cerial/schema` exports

| Export | Declares or builds |
|---|---|
| `model` | A model, optionally `abstract` |
| `object` | An embedded object type |
| `tuple` | A tuple type |
| `enum` | An enum (a reserved word, so import it with an alias) |
| `literal` | A literal union type |
| `f` | Field builders: `f.string()`, `f.record()`, `f.relation()` and the rest |
| `e` | Tuple element builders: `e.string()`, `e.self()` and the rest |
| `variant` | Literal variants: `variant.string()`, `variant.int()` and the rest |
| `Handle` | The type of a declaration, used to annotate a self-referencing one |

## The rules

Every page in this section assumes these.

1. **Export every declaration.** Only exported `model`, `object`, `tuple`, `enum` and `literal` declarations are part of the schema. A declaration that is not exported is not part of the schema.
2. **The first argument is the schema name.** `model('User', ...)` declares `User`. Keep the const and the name the same.
3. **A reference is a declaration, a function returning one, or a name.** Pass the declaration itself when it is already defined above. Pass a function (`() => Post`) when it is defined further down or the two refer to each other. A bare name string (`'Post'`) is an escape hatch for module graphs that import each other in a cycle. Prefer the first two, because TypeScript checks them and does not check a string.
4. **The schema entry is the unit of resolution.** All declarations of one schema entry resolve together, in any order. A declaration cannot refer to one in another schema entry, exactly as in `.cerial`. Cross-entry references are not possible.
5. **Names follow the same rules as in `.cerial`.** A name that is not a plain identifier, or is a property name of `Object.prototype` (`constructor`, `toString`, `valueOf` and the rest) or `prototype`, throws when the module loads. Declaration names cannot be JavaScript reserved words. See [Naming rules](/schema/overview/#naming-rules).

## Self-referencing declarations

A declaration cannot be passed to itself, because the const does not exist yet while its own initializer runs. Pass a function instead:

```typescript
import { f, model } from 'cerial/schema';

export const Folder = model('Folder', {
  id: f.record().id(),
  name: f.string(),
  parentId: f.record().optional(),
  parent: f.relation(() => Folder).optional().field('parentId'),
  children: f.reverse(() => Folder).array(),
});
```

If TypeScript reports that the const "implicitly has type 'any' because it is referenced in its own initializer", annotate it with `Handle` and give the function the same return type:

```typescript
import { f, model } from 'cerial/schema';
import type { Handle } from 'cerial/schema';

export const Category: Handle<'Category', string> = model('Category', {
  id: f.record().id(),
  name: f.string(),
  parentId: f.record().optional(),
  parent: f.relation((): Handle<'Category', string> => Category).optional().field('parentId'),
});
```

`Handle<Name, IdType>` takes the declaration name and the type of its id (`string` for a plain `Record`). Relations can still point at an annotated const, but it can no longer be the parent in an `extends`, so leave the annotation off a declaration you extend.

## Moving an existing schema

`cerial convert` rewrites a schema between the two forms in either direction and reports what it had to change. See [Convert](/cli/convert).
