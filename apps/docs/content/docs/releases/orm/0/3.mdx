## 0.3.0

**SurrealDB compatibility:** 4.0.0 | **SDK:** surrealdb 2.2.2

### Security

- Sub-keys of a `@flexible` object field were written into the query text
  without being quoted, while only the value was bound. A crafted sub-key could
  therefore change the statement around it. It is reachable wherever a sub-key
  comes from input rather than from your own code, such as a JSON filter body or
  a query-string filter forwarded into a `where` or an update. Affected
  surfaces: `where`, update `data`, an object sub-`select`, and `orderBy`.
  `create` was never affected, because the object travels as a bound value.
  Present in 0.1.0 and 0.2.0.

  Sub-keys of a flexible field are now quoted when written. Quoting rather than
  rejecting is deliberate: an undeclared sub-key is the whole point of
  `@flexible`, and a name check would have refused legitimate keys such as
  `my-key` or a non-ASCII name. Strict object fields reject an undeclared
  sub-key instead, which is a separate change listed under Fixed. If you forward
  user input into a flexible field, upgrade; until then allow-list the sub-keys
  you expect before they reach the call.

- `escapeIdent` and `escapeIdPart`, which the package re-exported from the
  `surrealdb` SDK, do not escape a backslash. A value that ends the quoted
  identifier early therefore leaves the quotes and runs as part of the
  statement. Run against a live database, a value passed through `escapeIdent`
  and written into a column position ran an injected `DELETE` and emptied
  another table, and a value passed through `escapeIdPart` into a record-id
  position did the same. Cerial's own queries never called either function, so
  only code that put their output into query text is affected. Present in 0.1.0
  and 0.2.0, which both exported them.

  Both are no longer exported. For an identifier use `sql.ident`, and bind
  values as parameters. The same flaw is in the SDK's string form of `Table` and
  `RecordId`: interpolating `String(new Table(name))` or
  `String(new RecordId('user', id))` into query text ran an injected `DELETE`
  in the same way. Those two classes are still exported, since they work as bound
  values. Bind them and never interpolate their string form. If you build query
  text from request input with the removed functions or those string forms,
  upgrade and switch to parameters.

- `orderBy`, `limit` and `offset` inside `include` were written into the query
  text without being checked, so a crafted value could run an extra `SELECT`
  and return rows from other tables under the included relation, including
  fields the call never selected. It needs no `@flexible` field. It is
  reachable wherever one of those values comes from request input, such as a
  JSON body passed straight into `include`, for example
  `include: { posts: { orderBy: body.sort } }`. Present in 0.1.0 and 0.2.0.

  These options are now checked against the included model before anything is
  built: an `orderBy` key that is not a field of it throws `Unknown field
  '<path>' on model <Model>`, a direction other than `asc` or `desc` throws, and
  `limit` and `offset` must be non-negative integers. Keys that are accepted are
  still quoted when written. If you forward user input into an include, upgrade;
  until then allow-list the `orderBy` keys, and cast `limit` and `offset` to
  integers, before they reach `include`.

- A composite `@@unique` key in `where` was never checked against its
  directive, so an empty or partial value silently dropped the missing parts
  from the filter. `deleteUnique({ where: { cityZip: {} } })` ran an
  unconditional `DELETE` and removed every row in the table, and a partial key
  such as `{ location: { city: 'NYC' } }` removed every row matching only that
  part. `updateUnique` and `upsert` widened the same way. The generated types
  already require the full shape, so a correctly typed call could not reach
  this; it was reachable from JavaScript, from casts, and from values that
  arrive at runtime, such as `deleteUnique({ where: { cityZip: body.key } })`.

  A composite value must now name every field of its `@@unique` directive,
  each as a plain value, with dotted paths written as nested objects. Anything
  else throws, naming the directive and what it requires. If you forward user
  input into a composite key, upgrade; until then check that every part is
  present before the call.

- A `where` that was supplied but compiled to no conditions left `deleteMany`,
  `updateMany`, `deleteUnique`, `updateUnique` and the update half of `upsert`
  running with no `WHERE` at all. `deleteMany({ where: { AND: [] } })`, a
  `where` whose values were all `undefined` (such as
  `{ email: body.email }` when the body has no email), a composite `@@unique`
  key (which `deleteMany` and `updateMany` never expanded), and an operator
  object on a unique field (`deleteUnique({ where: { email: { contains: 'x' } } })`)
  each removed or rewrote every row in the table.

  A destructive statement whose `where` has keys but compiles to nothing now
  throws, naming the model and saying that the filter resolved to no
  conditions. Leaving `where` out, or passing `{}`, still affects every row;
  that is how you ask for it. If you build a `where` from request input, upgrade;
  until then check that each value is defined before the call.

  Related changes in the same release: a unique filter takes plain values and
  throws on an operator object or an undefined part of an object `@unique`;
  composite keys now filter in `findMany`, `count`, `updateMany` and
  `deleteMany`, including inside `AND`, `OR` and `NOT`; `OR: []` and `NOT: {}`
  match no rows, in reads and writes alike; and a relation filter in
  `deleteMany` and `updateMany` now matches the rows it names instead of none.

- A `@default` value on a `Duration` field was written into the migration DDL
  unquoted whenever it merely *began* with a duration, so a crafted default
  could append statements of its own. `@default("1h; REMOVE TABLE victim")`
  emitted `DEFAULT 1h; REMOVE TABLE victim;` and dropped the table when the
  migration ran. Duration defaults are emitted unquoted by design, because
  SurrealDB needs `DEFAULT 1h30m` rather than a string, and the check that
  decided "this is a duration" matched a prefix instead of the whole value. It
  is reachable by anyone who can author or edit a `.cerial` schema, and it runs
  with whatever rights the migration runs with. Present in 0.1.0 and 0.2.0.

  A value is now emitted unquoted only when the whole of it is a duration, and
  anything else is emitted as a quoted string. `@default(1h30m)` is unchanged.
  A value that was never a valid duration, such as `@default("5 apples")`, used
  to produce DDL the database refused and is now a string default. Quoting
  rather than refusing keeps a malformed default from becoming a new generate-
  time failure for a schema that already migrates.

- `cerial generate` and `cerial format` imported a `cerial.config.ts` found anywhere
  beneath the working directory, and importing a TypeScript config executes it.
  Discovery globbed `**/cerial.config.{ts,json}` with no depth bound, skipping only
  `node_modules/` and the working directory itself, so running either command inside
  a project containing an untrusted `cerial.config.ts` ran that file. Present in
  0.1.0 and 0.2.0.

  Folder configs are now discovered only as direct children of the working directory
  or under `schemas/` and `schema/`. Multi-schema projects laid out the documented way
  are unaffected. Separately, a folder config that fails validation now stops the
  command with an `Invalid folder config` error instead of being skipped silently: the
  handler caught every error while claiming to catch only the root-style-config case,
  so a malformed config read as absent.

- Record ids reached query text through the SDK's own string form, and that
  escaping is defeatable. It escapes the closing bracket of a quoted id but
  leaves a backslash alone, so an id ending in a backslash before the bracket
  cancels the escape and closes the id early; whatever follows runs as part of
  the statement. Run against a live database, a crafted id passed to
  `findUnique`, `updateUnique` or `upsert` deleted every row of an unrelated
  table. It is reachable wherever an id comes from request input, such as a
  route parameter. Present in 0.1.0 and 0.2.0.

  Record ids are now bound as parameters at every site and never written into
  query text, so no escaper is involved. A nested create or upsert option now
  carries a record id rather than a string. If you pass ids from request input,
  upgrade; until then reject any id containing a backslash.

- In a nested create through a reverse relation, a key you passed became a
  column name in the query text without being checked or quoted. A key shaped
  to end the clause and start a statement ran that statement: a `DELETE`
  against an unrelated table removed rows while the create returned success.
  It is reachable through `create`, and the create half of `upsert`, wherever
  the keys of a nested create come from request input, such as
  `{ posts: { create: body.post } }`. Present in 0.1.0 and 0.2.0.

  Each key of a nested create is now checked against the target model, and an
  unknown key throws before any query is built. If you forward user input into
  a nested create, upgrade; until then allow-list its keys.

- The sort direction of an `orderBy` key under a `@flexible` object field was
  not validated, on the top-level `orderBy` and on `orderBy` inside `include`.
  An undeclared sub-key is accepted there by design, but its direction went
  into the query text unchecked, and forcing it to upper case did not help
  because the database is case-insensitive. Against a live database on the
  development branch, a crafted direction deleted every row of an unrelated
  table. Reach in a published version not established: the validator in 0.1.0
  and 0.2.0 had a different shape, though 0.2.0 already wrote the direction
  into the query text. Treat 0.1.0 and 0.2.0 as exposed.

  The direction is now checked against `asc` and `desc` for every sub-key,
  declared or not, and a nested object is checked recursively. If you forward
  user input into an `orderBy` on a flexible field, upgrade; until then allow
  only `asc` and `desc`.

- The operator lookup in `where` answered to every name on `Object.prototype`,
  so `where: { name: { toString: 1 } }` (and `constructor`) was treated as a
  registered operator, dropped the filter and matched every row. In a
  `deleteMany` or `updateMany` that is every row in the table. `hasOwnProperty`,
  `valueOf` and `__proto__` raised a raw `TypeError` instead. It is reachable
  wherever a filter body comes from request input. Present in 0.2.0.

  Operators are now looked up by own property, so a prototype name is reported
  as an unknown operator like any other. If you forward a JSON filter body,
  upgrade; until then allow-list the operator names you accept.

- Several names a `.cerial` schema can carry reached the generated client as
  code without being checked. Tuple element names and Record id types on object fields
  (the `Record(...)` parameters) were written into the generated model registry as
  they stood, so a crafted schema could make the registry run its own code in
  every process that imported the client. Digit-led names, names equal to a
  property of `Object.prototype` (`constructor`, `__proto__`) and declarations
  whose names differ only in case produced types that did not parse, printed a
  native function body into the types, dropped an enum value, or wrote two
  declarations to one file. It needs write access to a schema file, so it
  matters most where schemas come from a contributor, a package or generated
  input. Present in 0.2.0.

  Every name that reaches generated code, declaration names included, is now checked against one rule, and
  `Record(...)` types on object fields are validated like a model's. Generate
  refuses the schema, names the kind, owner and name, and writes nothing. See
  the Changed entries for the exact rules. Until you upgrade, review schema
  files from outside sources before running `cerial generate`.

- `cerial generate` removed every `.ts` file in its output directory that the
  run had not written, and `--clean` removed the whole directory, wherever
  `output` pointed. An output set to a parent folder, or to the project root,
  deleted your own source files, including TypeScript schema sources. The
  output can come from a flag, the root config, or a folder config found
  automatically. Present in 0.2.0.

  Generate now removes only files listed in the output's `.cerial-output.json`,
  and refuses an output outside the project root or one that holds schema
  sources. See the Changed entry on generate output.

- `cerial init` wrote the schema folder names it found into
  `cerial.config.ts` unescaped, and `generate` imports and runs that file. A
  folder with a crafted name therefore ran code the next time you generated. A
  folder name also became the generated client class name unchecked, so an
  unusual name produced a client that did not parse or ran text on import.
  Present in 0.2.0.

  `init` now writes names and paths as quoted data, and all schema names are
  validated before it becomes a class name. Review the config an older `init`
  wrote if the project holds folders you did not create.

- Inside `$transaction`, the executor rewrote transaction variable names by scanning the
  statement text. A `@flexible` sub-key in a `where` could steer that rewrite
  and make an upsert take its update path with the values meant for create,
  overwriting fields such as a role or a balance on an existing row. Present in
  0.2.0. Transaction items now run exactly as built, with no text rewriting. If
  you forward user input into a flexible field inside a transaction, upgrade.

- The exported builders, the low-level `build*` query functions exported from the package root
  (`buildFindManyQuery`, `buildCreateQuery` and the rest) wrote select keys,
  `orderBy` directions, `limit`, `offset`, compute keys and data keys into the
  statement without the checks the client methods apply. Cerial's own client
  was not affected; code that called these functions with request input was.
  Present in 0.2.0. They now validate their input the way the client does.

- The exported where helpers (`transformWhere`, `transformWhereClause` and
  `buildConditions`) skipped any key that named no field. A filter made only of
  such keys, for example a misspelt field or a `__proto__` key in a JSON body,
  came back as empty text, so code that composed its own statement from it,
  such as a `DELETE`, ran on every row. The client methods were not affected:
  they refuse unknown keys. Present in 0.2.0. The helpers now validate the
  `where` the way the client does, and refuse a filter that resolves to no
  conditions, such as `{ AND: [] }` or an empty relation filter. Without a model
  registry they also compiled a relation filter against the relation field
  itself, which is never stored, so `{ posts: { isNone: true } }` matched every
  row; they now refuse relation filters without a registry.

- An empty OR branch (`{}`, `{ AND: [] }`, an empty object field filter or a
  field set to `undefined`) was dropped instead of making the OR match every
  row. Under a `NOT` that widened the filter, in the client methods too:
  `deleteMany({ where: { NOT: { OR: [{}, { name: 'a' }] } } })` deleted every
  row except `a`, where the filter matches none. This reaches code that wraps a
  caller's filter in `OR` or `NOT`. Present in 0.2.0. An empty OR branch now
  makes the OR match every row, so a `NOT` around it matches none.

- An empty filter body was dropped instead of read for what it says:
  `some: {}` or `none: {}` on an array of objects, an array of tuples or a
  reverse relation, and an empty operator object such as `age: {}`. Beside
  another key or under `NOT` the filter widened, in the client methods too:
  `deleteMany` with `items: { none: {} }` beside a name filter removed every
  row with that name, not only those with no items. Present in 0.2.0.

- A relation inside a relation filter, such as
  `posts: { some: { author: { name: 'Ann' } } }`, compared the relation field
  to a value and never matched, so under `NOT` a `deleteMany` removed every row
  and cascaded to its children. Present in 0.2.0. Nested relation filters now
  follow the relation at every depth.

- A null on a reverse relation, which the types do not allow but a JSON body
  can carry, was ignored, so `{ isActive: true, posts: null }` removed every
  row through `deleteMany`. Present in 0.2.0. It is now refused.

- `deleteMany` and `updateMany` ran their filter inside the write, and the
  database re-evaluates a subquery for each row as the write proceeds. A
  relation filter that reads the table being written therefore saw earlier
  rows already removed or changed: a `deleteMany` whose filter matched one
  post removed two. Present in 0.2.0. Bulk writes now select the matching
  records first and write exactly those.

- A filter on a to-one relation, such as `manager: { name: { neq: 'x' } }`,
  read the related record's fields through the foreign key, so a row with no
  related record, or whose related record had been deleted, read them as empty
  and matched a negative operator. `deleteMany` with that filter also removed
  every employee with no manager. Present in 0.2.0. The filter now requires
  the related record to exist.

- Nested write field names could collide in the bound values of a statement and
  make one nested value overwrite or drop another. Every bound value now gets a
  unique name.

- Object fields in a relation filter were compared as one whole value instead
  of by sub-field. That is the same value test a plain equality uses, so a
  filter such as
  `none: { addr: { city: 'Oslo' } }` or
  `NOT: { manager: { addr: { city: 'Oslo' } } }` matched more rows than it
  says, in the client methods too: `deleteMany` with the second form removed
  rows the filter keeps. It covers object fields, arrays of objects and tuple
  fields, at any depth. Present in 0.2.0. These fields now compile by
  sub-field inside a relation filter, as they do at the top level of a `where`.

- A tuple index key in a filter, such as `coords: { 1: 5 }`, was read with a
  lenient number parse. A key like `'1 anything'` filtered on index 1, and a
  key holding a newline reached the refusal message unchanged, so a request body
  could write forged lines into a log that prints the message. Present in
  0.2.0. A tuple index key must now be all digits with no leading zero.

- An unknown operator below the top level of a `where` was dropped instead of
  refused. Under an object sub-field, an undeclared `@flexible` key, a tuple
  element or a relation body, `address: { city: { startsWith2: 'O' } }` added no
  condition, so the filter matched more rows than written. A malformed `AND`,
  `OR` or `NOT` body at those depths (a `NOT` that is not an object, an `AND`
  that is not an array, a `some` body that is not an object) compiled to no
  condition in the same way. In a `deleteMany` that removed rows the filter was
  meant to keep. It is reachable wherever a filter body comes from request
  input. Present in 0.2.0. Unknown operators and malformed logical bodies are
  now refused at every depth, and the query compiler throws on an operator it
  does not know instead of skipping it.

- A nested `create` inside a relation write skipped the validation a top-level
  `create` runs, and the value transform then coerced what was left. A date
  string written to an `Int` field of a nested record was stored as its year,
  and other wrong-typed values were stored without a check. Present
  in 0.2.0. Nested creates now run the same validation as a top-level `create`
  and refuse the call, naming the field.

- `push`, `set` and `unset` on an array of primitives accepted values of any
  type. A string pushed to an `Int[]` was accepted, where a `create` would have
  refused it. Present in 0.2.0. Each value is now checked
  against the element type, the way a `create` checks an element.

- A `Decimal` field accepted any string, `NaN` and `Infinity`. The SDK reads a
  prefix of the string and returns `0` for what it cannot parse, so `'1,5'`,
  `'12abc'` and `'NaN'` were stored as `0`, and a filter such as
  `price: { gt: 'abc' }` compared against `0`. Present in 0.2.0. A decimal must
  now be a finite number, a `CerialDecimal`, or a decimal string that reads in
  full. See the Changed entry on decimal values.

- The exported builders and `compile*` functions, and the `QueryBuilder`
  class, accepted a relation filter or a nested write without a model registry
  and dropped that part. A `NOT` around a relation filter then deleted every
  row, and nested `connect`, `create` and the other nested operations reported
  success without running. Cerial's own client always passes the registry and
  was not affected; code that called these functions directly was. Present in
  0.2.0. Both are now refused with a `CerialValidationError` that says the
  registry is required.

- `findUnique` by id read the rest of its `where` without the model registry,
  so a relation filter next to the id was ignored: `findUnique({ where: { id,
  posts: { none: {} } } })` returned the row whether or not it had posts. The
  Present in 0.2.0. The relation filter is now applied.

- A unique key passed as `undefined` still counted as the key that picks one
  row. `upsert({ where: { email: body.email, active: true }, ... })` with
  `email` missing from the request was treated as naming one row. It failed
  with a database error when several rows matched, created a new row instead
  of updating when `update` held a relation operation, and wrote to the matched
  row when exactly one matched. Present in 0.2.0. An `undefined` unique key, or
  an `undefined` part of an object `@unique` key, is now refused by name on
  `findUnique`, `updateUnique`, `deleteUnique` and `upsert`, before any query.
  `upsert` also writes at most one row now; see the Changed entry on `upsert`.

- A misspelled option key on a model method was ignored. `deleteMany({ wehre:
  { id } })` had no `where` and removed every row,. Present in 0.2.0. Every model method now
  refuses an option key it does not take and names it.

- `updateWhere`, and `unset` with a `where`, on an array of objects were
  accepted and typed but did nothing, so a call such as
  `update({ items: { updateWhere: { where: { sku: 'a' }, data: { qty: 2 } } } })`
  reported success and changed no element. Present in 0.2.0. They now throw and
  name the supported forms. See the Changed entry on object arrays.

- node_modules schemas: with no config, schema discovery searched every `schemas/` and `schema/` folder
  under the working directory, `node_modules` included, and used the first match.
  A dependency that shipped a `schemas/` folder replaced your schema: `generate`
  built a client from the package's models, and `migrate apply` with
  `--allow-destructive --allow-data-loss` dropped the tables your own schema
  declared. A TypeScript module in that folder also ran. The `.cerial` half is
  present in 0.2.0. Discovery now stays inside the project root, never enters
  `node_modules` and never follows a symlink that leaves the root. See the Changed
  entry on several schema folders.

- Format and convert writes: `cerial format` rewrote `.cerial` files inside `node_modules`, and inside a linked
  package that lives outside the project, whenever discovery reached them through
  the `schemas/` fallback or a root marker file. `cerial convert --remove-source`
  could write into and delete from those folders too. The `format` half is present
  in 0.2.0. Both commands now refuse to write or delete any path whose real path
  is outside the project root. See the Changed entry on writes outside the project
  root.

- Control characters in an echoed key: validation errors repeated the key, operator or
  path you passed exactly as given. A key holding a line feed, carriage return or
  escape character wrote those bytes into whatever showed the error, such as a log
  or a terminal, so a request body key could forge a log line or carry terminal
  escape sequences. It is reachable wherever a key comes from request input, such
  as a JSON filter or data body. Present in 0.2.0.

  Those messages now show control characters as escapes: line feed, carriage
  return, escape, bell, the other C0 and C1 control characters, and the Unicode line
  and paragraph separators. Ordinary keys print as before. If you match on an error
  message that echoes such a key, expect the escaped form. The same holds for the
  database text a failed call or `client.migrate()` repeats in its error, which can
  hold a value you stored or sent.

- Where operands of the wrong type: a where operand was passed to the database as
  given, so `deleteMany({ where: { age: { lte: '5' } } })` on an `Int` field compared
  the number to a string and removed or changed rows you did not mean, and a mistyped
  `in`, `between`, `has` or `contains` operand did the same on reads. It is reachable
  wherever a filter is built from request input, which never passed through
  TypeScript. Present in 0.2.0. Every where operand is now checked against its field
  with the rules `create` uses, and a mistake is refused before any query. See the
  Changed entry on where operand types.

- Date operands given as a string in a `where`: the string was compared as text
  against the stored datetimes instead of being converted to a date, and a text
  operand matches every datetime. `deleteMany({ where: { createdAt: { gte:
  '2021-06-01' } } })` removed every row, and `updateMany` with the same filter
  changed every row. Reads returned every row too. It is reachable wherever a
  date filter comes from request input, where a date is a string, so a filter
  built from a JSON body hit it with no cast. Present in 0.1.0 and 0.2.0, which
  did not convert where operands.

  Date operands are now converted the way `create` converts them, on every
  operator, at any depth and inside a relation filter. A string that is not a
  date is refused before any query, naming the field. A `Date` and a valid date
  string both work as before. If you filter dates by string, upgrade; until then
  pass a `Date` built with `new Date(value)` and check it with
  `Number.isNaN(date.getTime())`. See the Changed entry on where operand types.

- Typed operands inside a relation filter: a `where` on a related model passed
  its operands to the database unconverted, so a Duration, Uuid, Decimal or id
  was compared as text or as a plain object against the typed stored value,
  while the same filter on the model itself converted it. A range operator then
  matched the wrong rows and an equality matched none:
  `Kit.deleteMany({ where: { owner: { duration: { gt: '90m' } } } })` removed
  every kit when two of three owners matched, and `neq` on an id or a foreign key
  did the same. It covered a to-one relation, `some`, `every` and `none` on a
  reverse relation, and an array of foreign keys, and a filter built from a JSON
  body hit it with no cast. Present in 0.1.0 and 0.2.0, whose relation filters
  did not convert operands.

  Relation filters now convert every operand the way a filter on the model itself
  does, on every operator. A `CerialDuration`, `CerialUuid` or `CerialDecimal`
  works as well as a string, and a value that is not valid for the field is
  refused before any query, as before. If you filter through a relation by one
  of these types, upgrade.

- Geometry lists in a `where`: `in` and `notIn` on a Geometry field converted their
  operand only when its first member was a coordinate pair, so a list of GeoJSON
  objects or `CerialPoint` values reached the database unconverted and matched
  nothing. `Place.deleteMany({ where: { location: { notIn: [{ type: 'Point',
  coordinates: [2, 2] }] } } })` removed all three rows when two of them were
  outside the list, and the typed form `notIn: [new CerialPoint([2, 2])]` did the
  same. It covered `updateMany`, `$transaction` and relation filters, and a filter
  built from a JSON body hit it with no cast. Present in 0.1.0 and 0.2.0.

  A geometry list now converts member by member, whatever form each takes: a
  coordinate pair, a GeoJSON object, a Cerial geometry or a mix. One bare pair on
  `eq` or `neq` is still a single point. A member that is not a valid geometry is
  refused before any query, naming the field. If you filter a Geometry field with
  `in` or `notIn`, upgrade.

- Object array sub-fields dropped in an object update: an update that merges an
  object field wrote its sub-fields one by one and treated an array of objects
  inside it as another nested object, so nothing matched and the array was
  skipped with no error. `updateUnique({ where, data: { metadata: { children:
  [...] } } })` stored nothing and reported success, and `{ children: { push:
  item } }` added nothing, so old values stayed. Self-referencing objects, whose
  `children` list is exactly this shape, were the usual case. It applies to
  `updateUnique`, `updateMany` and the update half of `upsert`, and it is hit by
  ordinary code with no crafted input. Present in 0.1.0 and 0.2.0.

  An array of objects inside an object update is now written whole, or by
  `push` and `set`, as an array of objects directly on the model already was. If
  you worked around this by replacing the whole object with `{ set: ... }`, you
  can drop the workaround. Rows updated before the upgrade did not receive the
  array; re-run those updates.

- Object fields replaced in the update half of an `upsert` with a `where` other
  than `id`: `upsert({ where: { email }, create, update: { address: { city:
  'Oslo' } } })` replaced the stored `address` with `{ city: 'Oslo' }` and lost
  its `zip` and every other sub-field, and `update: { tags: { push: 'x' } }` on
  an object array stored the literal `{ push: 'x' }` as a value. An `upsert` by
  `id` and `updateUnique` merged correctly, so the same `update` behaved
  differently by the shape of the `where`. Present in 0.1.0 and 0.2.0.

  The update half now merges objects and applies `push` and `set` exactly as
  `updateUnique` does, whichever field the `where` uses. If you passed a partial
  object here and relied on it replacing the stored one, pass the whole object in
  `{ set: ... }`. Check objects that went through such an `upsert`: sub-fields
  you did not pass may be missing, and an object array may hold a stray
  `{ push }` entry.

### Added

- A raw query hatch for SurrealQL the typed API has no position for: graph
  edges, vector search, `GROUP BY`, table views and live queries. The `sql` tag
  builds a fragment whose interpolated values are always bound, and it plugs
  into four places: a `$raw` key in any `where`, a `compute` option on
  `findOne`, `findMany` and `findUnique` (sortable through `orderBy`),
  `$raw` for whole statements on the client, on a model and inside
  transactions, and `$live` for managed live subscriptions on the client and on
  a model. `sql.ident` quotes an identifier and `sql.int` renders a checked
  integer, because neither can be bound. See [Raw Queries](/queries/raw-queries).

  ```typescript
  import { sql } from 'cerial';

  const users = await client.db.User.findMany({
    where: { isActive: true, $raw: sql`->follows->user CONTAINS ${bobId}` },
    compute: { follows: sql<number>`count(->follows->user)` },
    orderBy: { follows: 'desc' },
  });
  ```

  A fragment skips membership, key-path, enum and data validation, and a
  whole-statement write skips `@readonly`, cascades and N:N sync. The type
  argument on `sql<T>`, `$raw<T>` and `$live<T>` is an unchecked claim. The
  static text of a template must never be built from caller input;
  `client.query()` remains the unchecked string path. `$live` resumes after a
  transport reconnect, but a server restart ends the iterator with a
  `CerialConnectionError`, so callers must catch it and resubscribe.

- A schema can now be written as TypeScript. Declare models, objects, tuples, enums
  and literals with the factories exported from `cerial/schema`, and `cerial generate`
  produces the same client as it does for `.cerial` files. `.cerial` stays the
  canonical form. See [TypeScript Schemas](/schema/typescript).

  ```typescript
  import { f, model } from 'cerial/schema';

  export const User = model('User', {
    id: f.record().id(),
    name: f.string(),
  });
  ```

- Cerial finds TypeScript schemas three ways: the `*.schema.ts` suffix, an entry module
  that default-exports `defineSchema({ models: [...] })`, and a list of files in the config.
  The modes are additive: one schema entry can use all three, and Cerial generates the
  union of what they find. Generation imports and runs this code, as it does for
  `cerial.config.ts`, and an entry module also runs every module it imports, so generate
  only from schemas you trust. See [Finding Your Schemas](/schema/typescript/discovery).

- A `*.schema.ts` file, an entry or a listed `.ts` file can sit beside `.cerial` files in one
  schema, and Cerial generates one client from both. A `.cerial` field can be typed by an
  object, tuple, literal or enum a TypeScript module declares, and the reverse. A module
  with no declaration contributes nothing. See
  [Finding Your Schemas](/schema/typescript/discovery).

- A schema entry that holds both `.cerial` files and TypeScript modules now gets a
  generated `cerial/handles.ts` under the schema root. TypeScript imports it to refer to
  a `.cerial` declaration, for example to `extends` one or to type a field with it, in
  both directions across the two forms, with pick, omit, `abstract` and `!!private`.
  `.cerial` files refer to TypeScript declarations by name and need no import. You will
  see the file appear after the first `cerial generate`; do not edit it, and add it to
  `.gitignore`. Until the first generate, your typechecker cannot resolve the import.
  Cerial never overwrites a `cerial/handles.ts` it did not write. See
  [Mixing .cerial and TypeScript](/schema/typescript/mixed).

- `schemas[].entry` points a schema at an entry module, and `schemas[].files` lists
  TypeScript modules by path (literal paths, no globs). Either can replace `path` or sit
  beside it. The `ignore`, `exclude` and `include` fields and `.cerialignore` apply to
  all three modes. See [Configuration](/cli/configuration).

- The TypeScript form has no `cerial format`, no editor diagnostics, no hover and no
  completion from the VS Code extension; these work on `.cerial` files only. See
  [Choosing a Schema Form](/schema/typescript/choosing).

- `cerial convert --to ts` rewrites `.cerial` files as TypeScript modules, and
  `cerial convert --to cerial` rewrites TypeScript modules back into `.cerial`
  files. Each run is verified before it writes: the converted files must rebuild
  the same schema, or nothing is written and the report says why. A schema source
  is never overwritten, and `--force` only replaces earlier output.
  `--partial` converts what it can, holds back declarations that depend on a
  refused one and lists them, and still exits 1. `--remove-source` deletes the
  sources that were fully converted, after the output is written. Conversion to
  `.cerial` drops TypeScript comments and carries only declarations, not helpers
  or other code in a module; the report names each module that holds some. See
  [Convert](/cli/convert).

- `cerial migrate` inspects the live database and changes it to match your
  schema, for deployments where a change should be seen before it runs.
  `status` reports whether the database is in sync (exit 0), drifted or pending
  (exit 1) or unreachable (exit 2). `plan` writes the pending changes to a
  timestamped `.surql` file with destructive statements commented out. `apply`
  runs them, from the schema with `--from-schema` or from a reviewed plan file
  with `apply <file>`; destructive changes need `--allow-destructive`, and
  removing a table also needs `--allow-data-loss`. `baseline` records the
  current database as applied without running any DDL. There are no `down`
  migrations. Connection values come from flags, `CERIAL_DB_*` environment
  variables or your config, and there is no password flag. See
  [Migrate](/cli/migrate).

  ```bash
  bunx cerial migrate status
  bunx cerial migrate plan
  bunx cerial migrate apply --from-schema
  ```

- `parse()` and `parseWithLexer()` take an optional last argument, the path of the
  schema file being parsed, and every node in the returned AST records it in a new
  `origin` field (`{ kind: 'dsl', file, range }`). Calls that leave it out keep
  working and get the file name `<input>`. The `Origin` type and the
  `createDslOrigin(range?, file?)` helper are exported from `cerial` and
  `cerial/parser`.

- `@default`, `@defaultAlways`, `@createdAt` and `@updatedAt` on a tuple element
  now fill an element you leave out. Before, they were accepted and then did
  nothing: Cerial left the position empty, SurrealDB refused the fixed-length
  tuple, and a required `@createdAt` element made the row unwritable unless you
  supplied the timestamp yourself.

  ```cerial
  tuple Stamped {
    label String,
    born Date @createdAt,
    touched Date @updatedAt,
    hits Int @defaultAlways(7)
  }
  ```

  ```typescript
  await client.db.Page.create({ data: { name: 'home', stamp: { label: 'v1' } } });
  // stamp: ['v1', <now>, <now>, 7]
  ```

  Leave an element out by passing the tuple in object form without that key.
  A value you pass is always stored as given. `@updatedAt` and `@defaultAlways`
  elements are also refreshed by a per-element update that leaves them out;
  `@default` and `@createdAt` elements keep their stored value. Timestamps come
  from the database clock, like a model field's. Replacing the whole tuple with
  array form, and updating a different field, change nothing. `@uuid`, `@uuid4`
  and `@uuid7` remain unsupported on tuple elements. See
  [Decorators on Tuple Elements](/schema/tuple#decorators-on-tuple-elements).

- `orderBy` now accepts a relation field, so you can sort by a value on the
  related record:

  ```typescript
  const books = await client.db.Book.findMany({
    orderBy: { publisher: { name: 'asc' }, title: 'asc' },
    limit: 10,
  });
  ```

  The key is the relation, and its value names fields of the related model. It
  works on `findMany`, together with `select`, `where`, `limit` and `offset`,
  and mixes freely with ordinary and object-field keys in the
  order you write them. A path can cross more than one relation
  (`{ parent: { parent: { name: 'asc' } } }`) and can end in an object
  sub-field of the related model. Rows whose relation is unset or `null` sort
  before every value ascending and after every value descending.

  Only a forward, single-valued relation can be ordered. A reverse relation and
  a relation over an array of ids have no single value to sort by, so they are
  rejected with a message naming the field and the model, and the generated
  `{Model}OrderBy` type does not offer them.

  An earlier entry on this page, under Changed, rejected relation fields in
  `orderBy`. That rejection rested on a wrong conclusion: SurrealDB does not sort
  on a bare record-link path such as `authorId.name`, but it does sort on a
  projected alias of it. Cerial now projects the related value under an internal
  alias, sorts and pages on that, and removes the alias before rows are returned.

- `orderBy` inside `include` takes the same shapes as a top-level `orderBy` on
  the included model: object sub-fields and forward relations as well as plain
  fields.

  ```typescript
  const companies = await client.db.Company.findMany({
    include: { employees: { orderBy: { homeAddress: { city: 'asc' } } } },
  });
  ```

  A nested value for a field that has no sub-fields used to fail with a raw
  `TypeError`. It now throws a message naming the field and the model.

- Cerial now raises typed errors. `CerialError` is the base class and carries a
  stable `code`, the `model`, `operation` and `field` where they apply, and the
  underlying error as `cause`. Ten subclasses cover connection, unknown model
  and field, migration, validation, transaction, unique-constraint, database
  and generation failures, all exported from `cerial`, so a duplicate key can
  be caught with `instanceof CerialUniqueConstraintError` without matching on
  prose. See the Errors page for the full list and the code each carries.

- A write that violates a unique index now throws `CerialUniqueConstraintError`
  instead of an unclassified database error. It names the index and the
  conflicting value, so a caller can branch without reading the message:

  ```typescript
  try {
    await client.db.User.create({ data: { email: 'ada@example.com', name: 'Ada', isActive: true } });
  } catch (e) {
    if (e instanceof CerialUniqueConstraintError) {
      console.log(e.index, e.value, e.record); // the index, 'ada@example.com', the record that holds it
    }
  }
  ```

  `value` is the conflicting value as the database prints it (`'ada@example.com'`,
  `5`, `['a', 1]`), not a parsed JavaScript value.

  Creating a record whose `id` is already taken throws the same class, so one
  `catch` covers both. `e.conflict` tells them apart: `'index'` for a unique
  index (`index` and `value` are set) and `'record'` for a taken id (they are
  `undefined`). `record` is set in both cases.

  A unique violation raised by an `upsert` that matches by `id` is not classified
  yet: the driver reports it as a failed transaction without the index.

- A query made on a connection that has dropped, or whose reconnect attempts ran
  out, now throws `CerialConnectionError` with the driver error as `cause`,
  instead of the driver's own error. `commit()` and `cancel()` on a manual
  transaction are classified the same way, and any other database failure on
  them is now a `CerialDatabaseError` (no `model`). Using a transaction after it
  was committed or cancelled already threw `CerialTransactionError`.

- `create` and `updateMany` now accept `include`, on any model that has
  relations, returning the related records with the written ones:

  ```typescript
  const user = await client.db.User.create({
    data: { email: 'jane@example.com', name: 'Jane', isActive: true },
    include: { posts: true },
  });
  // user: User & { posts: Post[] }
  ```

  It takes the same values as `include` on `findMany` and combines with
  `select`, which narrows the base fields only. It works with nested relation
  operations in the same call. An unknown relation name throws before anything is
  written. `updateUnique` and `upsert` already accepted `include`.

- `includeStatementInErrors` is a new client option. A database error carries
  the model and the operation that produced it either way; with the option on,
  `error.statement` also holds the generated statement:

  ```typescript
  const client = new CerialClient({ includeStatementInErrors: true });
  ```

  It is off by default. The statement includes the bound parameter values
  (`error.statement.vars`), which are your data, so an error that reaches a log
  or an error tracker would carry them. Turn it on in development, not where
  errors are shipped elsewhere. The `statement` is the call's main statement; a
  nested write may run others.

### Fixed

- `create`, `createMany` and nested creates now refuse an undeclared key in a strict
  object field before any query, naming the field, as updates already did. Before,
  the database refused it and its error repeated the key as given.

- Regenerating now removes an output directory whose files were all stale, such
  as `internal/registry/objects/` after the last object is deleted from the
  schema. Before, the empty directory stayed behind.

- `cerial generate --watch` now honours folder-level configs when there is no
  root config. Before, a watch run without a root config ignored them.

- Regeneration in watch mode now applies `.cerialignore`, the config `exclude`,
  `entry`, listed `files` and the connection settings the same way a plain
  `cerial generate` does. Before, a watch rebuild could include schema files
  that a one-shot run excluded.

- A database error from an item of an array `$transaction` now throws a
  `CerialDatabaseError` (or `CerialUniqueConstraintError`), as callback mode
  does. Before, it reached your code as the raw driver error, so a check such as
  `error instanceof ValidationError` needs to read `error.cause` instead.

- `deleteUnique` by `id` now honours the other keys in its `where`. Before, an
  `id` beside another key (`{ id, name }`, or `{ id, $raw: ... }`) took the id
  shortcut and the other keys were dropped, so the row was deleted whatever
  they said. A call that relied on that now deletes only when every key
  matches, and with `return: true` it gives `false` when nothing was deleted.

- `cerial generate` named the wrong schema file in some validation errors. It
  picked the first file whose text contained `model <Name>`, so an error on
  `model User` in `b.cerial` was reported against `a.cerial` when that file held
  `model UserProfile`, and an error on a model that extends a parent in another
  file could name the parent's file or none. Errors now name the file that
  declares the model.

- `findOne` now accepts `orderBy` in its generated type. The runtime and the
  documentation always supported it, and it is how you choose which record is
  "first", but the type omitted it, so a correct call needed a `@ts-expect-error`.

- Deleting a record now prepares its dependent models first. A `deleteMany` or
  `deleteUnique` that cascades to a model nothing had touched yet failed with an
  error saying the dependent table did not exist, instead of deleting. It
  affected every `@onDelete` strategy that reaches the dependent table, including
  `Restrict`, and was most likely to appear as the first delete a process ran.

- Nested writes and `include` now migrate the models they reach. Previously only
  the model you queried was migrated, so the first nested create, nested connect
  or `include` touching a related model reached a table SurrealDB had never been
  told about. SurrealDB created that table implicitly and without a schema, and
  the migration that arrived later applied a schema over rows already written
  without one.

  Two failures followed, both of which needed manual repair in the database:

  - A field with a server-side default (`@createdAt`, `@updatedAt`, `@uuid`) was
    missing from rows written before the table was defined, because nothing had
    yet declared the default. Once the field was defined, every later write to
    those rows failed with a coercion error reporting that a `datetime` was
    expected but `NONE` was found.
  - A `@@unique` index could not be built over rows that already violated it, so
    the index was never created and duplicate values kept being accepted with
    nothing reporting a problem.

  Array-mode `$transaction` had the same gap and migrated only each queued
  query's own model. Callback and manual transaction modes were never affected,
  because both already migrate every model.

- Unknown field names in `data` are now rejected on create and update instead of
  being silently dropped. A typo such as `{ emial: 'a@b.c' }` used to succeed
  while writing nothing for that field and reporting no error. It now throws,
  naming the key and the model.

  A key is unknown only when the model has no such field. Fields that exist but
  are excluded from an input type for another reason, such as a `@now` field
  being computed, are still accepted and ignored as before. Sub-keys of
  `@flexible` object fields are unaffected.

- Unknown sub-keys of a strict object in `data` are now rejected on update
  instead of being silently dropped. A typo such as
  `data: { address: { cty: 'NYC' } }` on an object field that is not `@flexible`
  used to be skipped, and when it was the only key the update wrote nothing and
  still reported success. It now throws, naming the full path from the model
  (`address.cty`) and the model.

  The check applies to `updateMany`, `updateUnique` and the update half of
  `upsert`, at any depth, including objects inside tuples and the element keys
  of a tuple updated in object form. `@flexible` is a property of the field, not
  of the object type, so the same object type accepts undeclared sub-keys on a
  `@flexible` field and rejects them on a strict one.

  A value written whole is checked the same way: the contents of
  `{ set: ... }`, an element of an array of objects and a `push` item. Before,
  its top level skipped the check. A self-referencing object, which the database
  accepts any key in, therefore stored `{ set: { ...tree, extra: 1 } }` with the
  undeclared key intact, and a strict object did the same for `{ set }` on
  `updateUnique`, `updateMany` and the update half of `upsert`. These now throw,
  naming the full path (`metadata.children[0].extra`) and leaving the row
  untouched. A `@flexible` field still accepts undeclared keys there.

- Unknown sub-keys of a strict object in `unset` are now rejected the same
  way. `unset: { address: { cty: true } }` used to emit a write to a path that
  does not exist and report success while changing nothing. It now throws with
  the same message as the equivalent `data` value, on `updateMany`,
  `updateUnique` and the update half of `upsert`.

- A key that the related model does not have is now rejected inside a relation
  filter. `findMany({ where: { author: { nmae: 'Ada' } } })` used to ignore the
  unknown key, so the filter vanished and more rows came back than asked for.
  It now throws, naming the key and the related model, and the same applies
  inside `some`, `every` and `none` on array relations and under
  `AND`/`OR`/`NOT`. An array relation filter accepts only `some`, `every` and
  `none` as keys.

- A write whose `data` touched a relation, with a `create`, `connect`,
  `disconnect` or `set` on a relation field, behaved differently from the same
  write without it. `updateMany`, `updateUnique`, `upsert` and `create` now treat
  the two the same. If a call that attaches or detaches a relation alongside
  ordinary fields ever returned something odd, this is the cause. Seven things
  were wrong:

  - `where` was cut down to its first key. With `updateUnique({ where: { id,
    version }, data })` the `version` guard was dropped, so the update was
    written even when the guard did not match and the row came back as if it had.
    `updateMany` updated every row matching only the first key. A first key that
    was a filter object such as `{ age: { gt: 5 } }`, or `OR` or `NOT`, matched
    nothing. The whole `where` is now applied, and a `where` that matches no row
    writes nothing, links nothing and returns `null` (or `false` for
    `return: true`).
  - `unset` was ignored, so a field you asked to clear stayed set.
  - `@updatedAt` was not bumped.
  - A partial object update replaced the whole object. Updating
    `meta: { industry }` dropped the object's other keys, and a partial update of
    a required object failed with a coercion error. It now merges, as it does
    without a relation in the call.
  - `return: 'before'` returned the row as it was after the update, and
    `return: true` reported `true` for an update that matched nothing. `'before'`
    now returns the prior row, including its relations as they were before any
    `connect` or `disconnect` in the same call, and `true` is `false` when nothing
    matched.
  - `select` was ignored and the full row came back.
  - `include` returned no relation. Both now behave as they do on a plain write,
    including on both halves of `upsert`, and an unknown or non-relation `include`
    key throws before anything is written.

- An `upsert` that created its row, with a `create`, `connect`, `disconnect` or
  `set` on a relation field in its `create` payload, ignored the id in its
  `where` and stored the row under a generated id instead. Reading it back by the
  id you upserted on returned `null`, so the row looked as though it had never
  been written. The row is now created as the record the `where` names, as it is
  without the relation op.

- An `upsert` with a `connect`, `disconnect`, `set` or nested `create` on a
  relation field, run inside `$transaction([...])`, wrote the row and dropped
  the relation without an error: the row existed and nothing linked to it. The
  relation operation is now applied in array mode too, on whichever half runs,
  and the reverse side is kept in step. An operation on the half that does not
  run is ignored, as it is outside a transaction.

- An `upsert` with a relation operation in `create` or `update` and a `where`
  that is neither an `id` nor a `@unique` field silently dropped the operation.
  It now throws a `CerialValidationError` (`C3000`) naming the model and the
  operation. Such a `where` can match no row or several, so there is no single
  row to attach a relation to. Upsert on an `id` or a unique field, or write the
  relation with a separate `update`. The same `where` with no relation
  operation is unchanged.

- A `connect` or `set` on a relation, in `updateMany`, `updateUnique` or `upsert`,
  that named a record which does not exist stored the id anyway. The link pointed
  at nothing and `include` later resolved it to nothing. `create` refused the same
  input with a raw database error. Both now throw a `CerialValidationError`
  (`C3000`) naming the model, the field and the missing id, before anything is
  written, and the call changes nothing, including its other fields. `disconnect`
  of an id that is not linked is unchanged: it does nothing. The same check runs
  inside `$transaction`. In array mode a missing target throws a
  `CerialValidationError` instead of the database's own error, and so does a target
  deleted between the check and the write. In callback and manual mode a missing
  target throws a `CerialValidationError` you can catch, and the transaction carries
  on with its other writes.

- The 0.1.0 release notes listed the geometry collection decorator as
  `@collection`. The decorator is `@geoCollection`; `@collection` has never been
  accepted in a schema.

- `@sort(desc)` and `@sort(asc)` are now supported, and `@sort(desc)` sorts descending.
  Any unrecognised `@sort` argument, `desc` among them, was silently treated as
  ascending, so a field written as descending was sorted ascending with no error. An
  argument other than `true`, `false`, `asc` or `desc` is now a schema error naming the
  field. `@sort`, `@sort(true)` and `@sort(false)` are unchanged.
- An `Email[]` field could never be written. The migration emitted
  `ASSERT string::is_email($value)` against the whole array rather than its elements, so
  every write failed, including an empty array. The assert is now applied per element.
  The same fix covers the other validated string types on array fields.
- An enum or literal used as a direct tuple element, or a literal array inside an object
  field, emitted DDL the database refuses: `literal` is not a kind name in a SurrealDB
  type position, so migration failed with `expected a kind name`. Both now emit the
  declared variants, for example `['A' | 'B', int]` and `array<'A' | 'B'>`.

- A `format` key in a config file that shadowed a built-in object property, such as
  `toString` or `valueOf`, crashed the config validator with a `TypeError` instead of
  being skipped as an unknown key. Unknown format keys are now skipped whatever they
  are called.

- Regenerating a client no longer produces spurious diffs. Schema files were discovered in
  whatever order the filesystem returned them, so `client.ts`, the barrel files, the migrations
  and the model registry came out in a different order on each run, and a regenerated client
  showed changes in seven files even when no schema had changed. Discovery is now sorted, so
  the same schemas always produce the same bytes.
- A pooled connection whose session the server had already dropped was handed to the next
  caller. `connect()` reused a pooled connection on its reference count alone, and after a
  server restart the driver still reports such a connection as connected while the session
  behind it is gone. The first query then failed with a permissions error about anonymous
  access, which reads as a credentials problem rather than as a dropped connection. A pooled
  connection is now checked with a round trip before it is handed out, and one that does not
  answer is closed and replaced. A connection that answers is reused as before, so sharing
  one socket between clients is unaffected.
- Watch mode regenerated only one of two targets that watched the same directory. The change
  debounce was keyed on the schema path, so two targets sharing a path but writing to
  different output directories cancelled each other and whichever fired second won. Each
  target now has its own key. Watch mode also registered a signal handler on every call and
  never removed it, so the handlers accumulated across runs. Both `generate --watch` and
  `format --watch` are affected.
- `await using` and `using` on a manual transaction now cancel it when the scope ends, and
  the transaction cannot be committed afterwards. Both forms used to throw
  `CerialUnknownModelError` naming a model called `_state`, leave the transaction active and
  still committable, and replace any error thrown inside the scope with that one. The cause
  was the transaction proxy handing back symbol-keyed methods unbound, so disposal ran
  against the proxy rather than the transaction. `CLAUDE.md` recommends `await using` as the
  way to avoid a dropped transaction, so the recommended remedy did not work. Only the
  manual form is affected: the array form hands back no transaction to dispose, and the
  callback form ends its own transaction when the callback returns.
- A transaction whose `commit()` or `cancel()` threw reported `state` as `'active'`, so there
  was no way to tell the handle apart from a working one. It now reports `'cancelled'`, and a
  later `commit()`, `cancel()` or query through it throws `CerialTransactionError` with
  `Transaction already ended` rather than reaching the driver and returning its
  `Transaction not found`. The error raised by the failing call itself is unchanged. The state
  is `'cancelled'` rather than a new value because SurrealDB commits atomically: a commit that
  threw applied nothing and the server has already dropped the transaction.

- A schema's `connection` in `cerial.config` did nothing. The docs described per-schema
  connections from 0.1.0, and resolution worked, but the value never reached the
  generated client, so `connect()` always needed an argument. The generated client now
  embeds the `url`, `namespace` and `database` of its schema, and `connect()` with no
  argument uses them. An argument still wins and replaces them as a whole. Credentials
  are not embedded, so the generated directory stays safe to commit: a no-argument
  `connect()` reads `CERIAL_DB_USER` and `CERIAL_DB_PASS` when it runs, and sends no
  authentication when both are unset. A committed client now contains the connection
  `url`, `namespace` and `database`.

- `where` inside an `include` was ignored. `include: { posts: { where: { published: true } } }`
  type-checked and ran, and every related record came back. It now filters: the
  condition is checked against the included model and applied before `orderBy`,
  `limit` and `offset`, so those act on the filtered set. An unknown field or
  operator throws. On a relation to a single record, a `where` that excludes the
  related record returns `null` for that field.

  The generated type does not yet allow for that `null`: a required relation
  such as `post.author` is still typed as present. Guard the access when you
  filter a single relation.

- `AND`, `OR` and `NOT` inside a filter on a relation to a single record were
  dropped, and with them the whole `where`. `findMany({ where: { owner: { OR: [{ name: 'a' }, { name: 'b' }] } } })`
  returned every row in the table without an error, so a tenant-scoped list
  returned other tenants' rows. They now filter, nest, and combine with plain
  fields in the same relation filter. `count`, `exists`, `updateMany` and
  `deleteMany` accepted or refused this shape differently from `findMany`; all
  six now compile it the same way, and a relation filter that has keys but
  resolves to no condition throws rather than matching everything.

  On an array relation (`Relation[]`) the operators go inside `some`, `every` or
  `none`, where they were also ignored before and now work. Directly under an
  array relation they are rejected like any other key that is not a quantifier.

- `cerial migrate` (`apply`, `status`, `baseline` and plan-file runs) now escapes control
  characters in the errors it prints, keeping its own line breaks. A server error
  that quoted stored data could otherwise carry terminal escape sequences into
  your shell. Ordinary text prints as before.

### Changed

- Where operand types are now checked against the field they filter, on reads and writes,
  at every depth: plain fields, sized numbers, dates, ids, UUIDs, durations, bytes,
  decimals, enum and literal members, object sub-fields and tuple elements. This covers
  `eq`, `neq`, `not`, `gt`, `gte`, `lt`, `lte`, `in`, `notIn`, `between`, `has`, `hasAll`
  and `hasAny` (each element), the `contains`, `startsWith` and `endsWith` strings, the
  boolean `isNull`, `isNone`, `isDefined` and `isEmpty`, and the shorthand
  `{ field: value }`. A wrong operand throws a validation error that names the field
  path and the expected type. The generated types already reject these operands, so
  only a call that bypasses them (a cast, plain JavaScript, a JSON body) is affected.
  Pass a value of the field's type: a number for `Int`, a `Date` or a date string for
  `Date`, an enum member for an enum, `null` only for a `@nullable` or optional field.
  Undeclared keys of a `@flexible` object stay untyped.

- Generated models, objects, tuples and literals are now `.d.ts` files by
  default, with `export type *` barrels (`enums/` stays `.ts`). With
  `skipLibCheck: true` this cuts type checking a 500-model schema on
  TypeScript 5.9 from 10.8 s to 0.50 s and memory from 2,136 MB to 779 MB, and
  on TypeScript 7 from 1.4 s to 0.14 s. With `skipLibCheck: false` it is no
  slower than before. Deep imports such as `./db-client/models/user` must be
  `import type`, and `*.d.ts` must not be in `.gitignore` when you commit the
  output. A library that re-exports generated types must copy the declarations
  after `tsc --declaration`, or the types become `any` without an error. Set the
  new `typeFiles: 'ts'` option to keep the old layout. See
  [Generated Output](/cli/generated-output#why-declaration-files) and
  [`typeFiles`](/cli/configuration#typefiles).

- The generated runtime registry and migrations are now written as chunk files of
  50 entries each, so no single generated file grows with the schema. Before, a
  2,500-model schema produced a 14 MB registry file that overflowed the TypeScript
  5.9 parser's stack. `internal/model-registry.ts` and `internal/migrations.ts`
  keep their names and exports, so imports do not change. The chunks sit under
  `internal/registry/` and `internal/migrations/`, and they are `.ts` files with
  either `typeFiles` value. See
  [Generated Output](/cli/generated-output#internalmodel-registryts).

- **Breaking.** `writeModelRegistry` and `writeMigrationFile`, exported from
  `cerial/generators`, now resolve to `string[]`, every path they wrote, instead
  of one `string`. Code that used the resolved value as a single path needs to
  read the first entry, or loop over the list.

- **Breaking.** Cerial now requires Node.js 22.12 or newer (`engines` is `>=22.12.0`).
  Node 20 is no longer supported. TypeScript configs and schemas are loaded through
  `jiti`, because Node's own type stripping cannot load them on any Node 22 release.
  Bun is unaffected.

- **Behavior change.** A delete now follows `@onDelete(Cascade)` (and required
  relations) through every level. In 0.2.0 it removed the direct dependents only and
  left their own dependents behind with dangling links, so a delete can now remove
  more rows than before: grandchildren and deeper. `Restrict` is checked across the
  whole reachable graph and blocks the delete from any depth, `SetNull`, `SetNone`
  and `NoAction` stop at their level, and a cycle terminates. A cascade deeper than
  16 levels is refused with nothing removed. To keep the 0.2.0 shape, give the
  second-level relation a non-Cascade action, for example `@onDelete(SetNull)`,
  so the walk stops there. See [Delete Behavior](/relations/on-delete/#how-deletes-walk-the-graph).

- A duplicate model, object, tuple, enum or literal name now reports where both
  declarations are, each as `file:line`, whether they come from `.cerial` files or
  TypeScript modules.

  **Behavior change.** Two declarations sharing a name are now refused and no client is
  written. Earlier releases did not check, so a project whose `.cerial` files already
  declared the same name twice generated silently and now fails. Rename one declaration.
  The check covers a name used by two kinds (a model and an object) and a collision
  between a `.cerial` file and a TypeScript module.

- `cerial generate --watch` also regenerates when a module an entry imports from outside
  its folder, or a listed file, changes. `cerial format` and `generate --format` format
  the `.cerial` files listed in `files` for a schema with no `path`, and leave TypeScript
  modules untouched.

- **Breaking.** The AST node types exported from `cerial` (`ASTModel`, `ASTField`,
  `ASTDecorator`, `ASTEnum` and the other node types) now require an `origin`.
  Nodes made with `createModel`, `createField` and the other factories get one
  automatically. A node written as an object literal needs
  `origin: createDslOrigin(range, file)`.

- `cerial format` writes decorator arguments in one canonical form instead of
  keeping how each was typed: `@sort`, `@sort()` and `@sort(true)` become
  `@sort(asc)`, `@sort(false)` becomes `@sort(desc)`, string defaults use single
  quotes, `@default(1.0)` becomes `@default(1)`, and a quoted duration default is
  written bare. Each form means the same thing and generates the same output, so
  the first `format` run after upgrading rewrites these spellings once, and
  `format --check` reports those files until it does.
- Transaction conflict retries (`TransactionOptions.retries`) now recognise a
  conflict from the structured error the server sends, not from the wording of
  its message. SurrealDB sends that detail from 3.1.0 and this release targets
  4.0.0. A server older than 3.1.0 reports conflicts without it, so those
  conflicts are no longer retried.
- **Breaking.** Enum and literal field values are now checked against the variants the
  schema permits. `status: 'actve'` on an enum allowing only `active` and `archived`
  used to pass Cerial untouched and be left for SurrealDB to reject. The error names
  the permitted values. Array fields are checked per element and the message carries
  the index.

  Typed code was already protected by the generated union type, so this matters most
  for values arriving from JSON, untyped callers, or anywhere a type assertion was
  used. A `broadType` variant such as `String` still accepts any value of that type,
  and object and tuple variants are matched by kind rather than deep shape, which the
  database continues to enforce.

  The check also reaches enum and literal fields nested inside objects and tuples, at
  any depth, in create data and in update data. Object fields, tuple elements, and
  arrays of either are covered, including the items of a `push` and the contents of a
  `set`. The error carries the path from the model, for example
  `top.mid.leaf.grade must be one of: 'LOW', 'MID', 'HIGH' (received 'NOPE')`.
  Previously a nested value outside the variants was left entirely to the database.
- **Breaking.** Sub-field names inside a `where` filter are now validated. Object
  and tuple filters were handed to the query builder unchecked, and the builder
  passed anything it did not recognise straight through as if the object were
  `@flexible` without ever checking that it was. A typo such as
  `where: { address: { cty: 'NYC' } }` on a strict object produced a condition
  that matched nothing, so you got an empty result rather than an error.

  Validated now at any depth: object sub-keys, `AND`/`OR`/`NOT` inside an object
  filter, the `some`/`every`/`none` quantifiers on array-object fields, and tuple
  elements by name or index. `@flexible` object fields still accept undeclared
  sub-keys, and flexibility is read per field, so the same object type can be
  flexible on one field and strict on another.

  Filtering through a relation is unchanged and still unvalidated.
- **Breaking.** `select`, `orderBy`, `limit` and `offset` are now validated before
  a query is built. A field name the model does not have is rejected in `select`
  and `orderBy`, including sub-keys of object and tuple selects. A typo used to
  return rows with the field quietly missing, or in `orderBy` to return rows in
  insertion order.

  Also rejected now: a sort direction other than `asc` or `desc`; a nested path
  under a field that has no sub-fields; and a `limit` or `offset` that is not a
  non-negative integer. Ordering by a relation field was rejected too in the
  first form of this change; it is supported again, see Added.

  Unaffected: `@flexible` object fields still accept undeclared sub-keys,
  ordering by a sub-field of a declared object still works, and `0` remains a
  valid `limit` and `offset`.
- **Breaking.** `findOne` now rejects `limit` and `offset`, and `findUnique`
  rejects `orderBy`, `limit` and `offset`, with a `CerialValidationError` naming
  the option. The generated types already leave these out, so typed code cannot
  reach this. From JavaScript or a cast they used to be accepted without effect:
  `findOne` forced its own `limit` of 1 but still applied an `offset`, so
  `findOne({ offset: 1 })` returned the second row, and `findUnique` validated an
  `orderBy` it never used. Use `findMany` to page.
- **Breaking.** A key that does not exist is now rejected in `select`, `orderBy`
  and `include` whatever its value, so `{ psots: false }` is an error rather than
  being read as opting out of a relation that was never there. Setting a key that
  *does* exist to a falsy value still opts out silently.
- **Breaking.** An `include` key that does not name a relation on the model now
  throws instead of being quietly dropped. A typo used to return a result with
  the relation simply missing, which was indistinguishable from a record that had
  no related rows. A key naming a real field of the wrong kind, such as a scalar,
  gets its own message saying what the field actually is. Setting a relation to
  `false` or `undefined` is still an opt-out, not an error.
- Upgraded the bundled SurrealDB JavaScript SDK (`surrealdb`) from 2.0.4 to 2.0.9.
- **Breaking.** 0.3.0 requires SurrealDB 4.0.0. SurrealDB 3.x is no longer
  supported, and 0.2.x remains on 3.1.5 for anyone who stays there. The full suite
  is tested against 4.0.0; see the SurrealDB Compatibility page.
- **Breaking.** 0.3.0 requires `surrealdb` 2.2.1 (it was 2.0.4 in 0.2.x).
  Upgrade the SDK before you upgrade the server, then move the server to 4.0.0.
  The server upgrade is one-way: a database that SurrealDB 4.0 has written to
  cannot go back to 3.x, so take a backup first.
- **Breaking.** `cerial migrate` follows SurrealDB 4.0's compatibility level 4.
  Removing a field deletes its stored values from every row, so the plan marks it
  destructive and says so. Changing a field's type over existing rows converts
  each value, and a value that does not convert gets the field's `@default`, or
  is cleared when the field is optional. That overwrites data, so it needs
  `--allow-data-loss` as well as `--allow-destructive`. A type change with
  neither a `@default` nor an optional field is a plan error that names the
  field and the fix. See [Migrations](/connection/migrations).
- `Decimal[]` fields can now use `@set`. 0.2.x refused the combination. See
  [@set](/schema/decorators/arrays/set).
- Wrong members of a tuple or literal are refused on `create` and on every update
  form, instead of being left for the database to reject.
- **Breaking.** A typed `@id` that SurrealDB cannot generate is now required in
  `create`. This affects `Record(int)`, `Record(number)`, and tuple and object
  ids, which were previously optional in the generated `Create` type even though
  the database rejects a create without them. `Record(uuid)`, `Record(string)`
  and plain `Record @id` are unchanged and still optional.
- **Breaking.** Union IDs now require an explicit id in `create`, including unions
  that contain `string` or `uuid` such as `Record(string, int)` or
  `Record(uuid, int)`. SurrealDB 4.0 refuses to generate a record id when the
  `id` field is a union type, so omitting the id is now a compile error and would
  fail at runtime. Plain `Record @id`, `Record(string)` and `Record(uuid)` are
  unchanged and still generate their id.
- **Breaking.** Passing a field name that is not on the model to `create`,
  `update`, `updateMany`, `updateUnique` or `upsert` now throws. Code that
  relied on stray keys being ignored must drop them.
- **Breaking.** `BeforeQueryCallback` now receives every model name an operation
  touches instead of a single name, so its signature changes from
  `(modelName: string) => Promise<void>` to `(modelNames: string[]) => Promise<void>`.
  This affects you only if you pass `onBeforeQuery` when constructing the client.

  ```ts
  // before
  onBeforeQuery: async (modelName) => log(modelName)

  // after
  onBeforeQuery: async (modelNames) => modelNames.forEach(log)
  ```
- An unknown field in a top-level `where` now reads
  `Unknown field 'nmae' on model User`, the wording every other surface already
  used, where it used to read `Invalid where clause: Unknown field: nmae`. The
  same wording now covers `unset`. `upsert` reports a rejected `create` or
  `update` payload as `Invalid data`, since a caller does not know which half
  would have run. Code that matched on the old wording needs updating; branch on
  the error class or `code` instead.
- **Breaking.** A write that touches a relation now returns what the same write
  without a relation returns, and applies the whole `where`, `unset`, `@updatedAt`,
  object merging, `return`, `select` and `include`; see the matching entry under
  Fixed. Code that depended on the old results needs updating: a guarded
  `updateUnique` now yields `null` when its guard does not match, `updateMany`
  touches fewer rows, `return: 'before'` no longer holds the new values, and a
  response you trimmed with `select` carries the fields a plain write returns
  rather than the whole row.
- **Breaking.** The root `cerial` entry now names every export instead of
  re-exporting whole modules, which takes it from 288 runtime exports to 201.
  Nothing was deleted: each name that left the root still resolves from the
  subpath that already held it, so an import from `'cerial'` that no longer
  resolves needs only a new module specifier.

  |---|---|
  | `createModel`, `createModelProxy`, `createProxyHandler`, `clearModelCache` | `cerial/client` |
  | Code generation and migration emitters: every `generate*` function, `mapToSurrealType`, `getTypeAssertion`, `hasTypeAssertion`, and the types `DefineFieldOptions`, `DefineTableOptions`, `SurrealQLType` | `cerial/generators` |

  import { chunk, generateMigrationQuery } from 'cerial';

  // after
  import { chunk } from 'cerial/utils';
  import { generateMigrationQuery } from 'cerial/generators';

  The root still exports every error class, every `Cerial*` value wrapper with

  `CerialAny`, `CerialSet`, `RecordIdInput`, `isRecordIdInput`, and the client
  names the generated code imports. Generated clients are unaffected. Separately,
  `cerial/cli` now has a `require` condition, so CommonJS code can load it.
- **Breaking.** Two exported type names changed because `surrealdb` exports the
  same names, which made an import from both packages collide. `Token` is now
  `CerialToken`, and the `ValidationError` interface (the result of validating a
  `where` filter) is now `CerialValidationIssue`. No alias is kept, since an
  alias would bring the collision back. The `CerialValidationError` class is
  unchanged. Rename the import if you used either type.
- **Breaking.** The `Cerial` class is created with `await Cerial.create(options)`.
  The constructor is private, so `new Cerial(...)` no longer compiles, and
  `create` is async because it may need to close a connection first.

  ```ts
  // before
  const cerial = new Cerial({ url, namespace, database, auth });

  // after
  const cerial = await Cerial.create({ url, namespace, database, auth });
  ```

  The three `onDuplicateConnection` modes now behave differently when a
  connection with the same `name` is already registered. They used to behave
  the same, and every construction opened a new client. `use_existing` (the
  default) returns the registered instance and opens nothing. `overwrite`
  disconnects the registered instance, then registers a new one. `throw`
  rejects with a `CerialConnectionError`, as before. If you relied on a second
  `use_existing` call replacing the first instance, pass `overwrite`.
- **Breaking.** `Model.upsert` now returns a typed result instead of `unknown`.
  Its return type is the union of the two generated overloads, `Model | null` or
  `Model[]` depending on the `where`, and `boolean` for `return: true`, so casts
  on the result can be removed. Anything was castable from `unknown`, so a cast
  to an unrelated type that used to compile is now an error: remove it, or
  narrow the union instead. Calls through the generated `client.db.<Model>`
  accessor already had these types and are unchanged.
- `updateMany` and `deleteMany` do not accept `orderBy`, `limit` or `offset`,
  and `deleteMany` does not accept `select` or `include`. The database has no
  ordering or paging on a bulk update or delete. To touch a limited set, read
  the ids with `findMany` first and pass them in `where`.
- **Breaking.** An error from the database now arrives as a `CerialDatabaseError`
  (`C6001`) naming the `model` and `operation`, with the driver's error as
  `cause`. A failed migration arrives as a `CerialMigrationError` (`C2002`).
  Before, both reached your code as the raw driver error with no sign of which
  call produced it. Code that matched the driver's error class on a caught error
  must read `error.cause` instead. An error Cerial already classifies, such as
  `CerialValidationError`, is unchanged. Failures of the `$transaction([...])`
  array form are not wrapped yet.
- **Breaking.** `disconnect()` now closes the connection it releases. Releasing a pooled
  connection decremented a reference count and cleared the model cache, but never closed the
  socket or removed the pool entry, so a disconnected client kept its connection open for the
  life of the process and only `resetConnectionPool()` freed anything. The last release now
  closes the socket and drops the entry, and a later `connect()` to the same URL opens a new
  one. While another client still holds the connection it stays open, so sharing is unchanged.
  If you called `disconnect()` and relied on the next `connect()` returning the same live
  socket, you now get a fresh connection instead.
- **Breaking.** A model, object, tuple or enum name, or a field name on a model or object,
  that is one of SurrealDB's reserved words is now refused by `cerial generate`. The error
  names the keyword and the declaration carrying it. Matching is case-insensitive and exact,
  so a name that merely contains a keyword, such as `ordering` or `contentType`, is still
  accepted.

  The names most likely to affect an existing schema are `type`, `content`, `order`, `group`,
  `table`, `value`, `timeout` and `access`, along with a model named `Order` or `Group` or an
  object named `Info`. The remedy is to rename the declaration: Cerial writes table and field
  names into the query text as they are, so there is no way to keep a reserved name by
  quoting it. Renaming a field changes the column SurrealDB stores, so an existing database
  needs the data moved across before the new schema is applied.

  Some of these words do work in SurrealDB today and are refused anyway, because the set it
  reserves has changed between versions and a name that parses now may stop parsing after an
  upgrade. One of them was already failing: a `select` on a field named `value` produced
  `SELECT value FROM ...`, which SurrealDB rejects outright, so that query had no working
  form. The list is pinned to SurrealDB 4.0.0.
- **Breaking.** `!!private` now holds across the whole `extends` chain. With
  `A extends B extends C`, a field marked `!!private` in `C` could be redeclared in `A`
  and `cerial generate` accepted it, so the modifier only protected a member from the
  direct child. It is now refused for model fields, object fields and tuple elements,
  and the error names the type that declared the member private rather than the one it
  was inherited through. `pick` and `omit` do not release the name: if `B` drops the
  member with `B extends C[!secret]`, `A extends B` still cannot declare `secret`. A
  schema that redeclared a grandparent's private member stops generating. Remove
  `!!private` from the declaring type, or rename the field in the child.
- `cerial generate` now refuses a config where two schemas define models that resolve to
  the same table, before writing any file. A config that generated before can now fail.
  Table names follow the model name in snake case, so `UserAccount` and `userAccount`
  collide. Two clients on one table wrote it with different shapes and failed on each
  other's fields. Rename one of the models, or give each schema its own `database` on its
  own `connection`: a shared table is allowed when every owner sets a different
  `database` itself, and is still refused when a database is equal, unset or only
  inherited from the root `connection`.

- Unknown keys in `select`, `include` and write `data` are now compile errors even
  next to valid keys; before, a typo beside a valid key compiled. This covers nested
  object selects, nested includes and nested `data` (object fields, tuple object
  elements, push and set elements, nested `connect` and `create` blocks), checked
  six levels deep. Beyond that, selecting and writing still work and the result is
  still narrowed. `@flexible` fields keep accepting undeclared keys. The editor now
  suggests the remaining keys after you type some. A typo reports
  `Type 'true' is not assignable to type 'never'` on the misspelt key. Code that
  relied on an unnoticed typo stops compiling. Files with many nested writes
  type-check about twice as slowly; other projects see no measurable change. See

  one-time diff after you regenerate.
- **Breaking.** A nested connect to a record that does not exist now throws.
  `create` used to surface the database's raw error and `updateUnique` and
  `updateMany` stored the dangling id, so a later `include` resolved to nothing.

- A nested updateUnique in `$transaction` array mode now returns the row, or
  `null`, not `[row]`, and `return: true` gives a boolean, matching the other

- **Breaking.** `cerial generate` refuses a SurrealDB reserved keyword used as a

  declaration or the generate fails and names it.

  `updateUnique` and `upsert`, naming the field, instead of reaching the

- **Breaking.** An empty OR (`OR: []`) and `NOT: {}` now match no rows, in reads and
  writes alike. A guard on a destructive call needs no extra handling.
- **Breaking.** A destructive where that has keys but compiles to no
  conditions throws on `deleteMany`, `updateMany`, `deleteUnique`,
  `updateUnique` and the update half of `upsert`, instead of touching every row.

  matching nothing. Use `$raw` only as a `where` key, a `compute` entry or a

- **Breaking.** On SurrealDB 4.0, a REMOVE FIELD in `cerial migrate` (or a

  rather than as per-element field definitions. The plan marks removals as

- **Breaking.** A model's `<Model>Select` and an object's `<Object>Select` type is
  now `AtLeastOne<...SelectFields>`, so an empty `select: {}` is a type error and
  the editor suggests the remaining keys after you type some. Pass at least one
  key, or omit `select`.
- **Breaking.** Names in a schema are checked before anything is generated.
  Tuple element names, field names, enum values and literal values are refused
  when they equal a property of `Object.prototype` (`constructor`, `__proto__`,
  `toString`, `valueOf`, `hasOwnProperty`) or `prototype`, and tuple element
  names, literal, tuple and enum names and `@@index` or `@@unique` names must
  be plain identifiers, so `7E` and `x-1` are refused. A declaration name that
  is a JavaScript reserved word (`class`, `delete`) is refused too. Rename the
  offender; the error names the kind, owner and name.
- **Breaking.** Declaration names are checked against each other. Two names
  that differ only in case (`Post` and `POST`), `index` in any casing, a name
  equal to another declaration's generated type (a model `PostWhere` beside
  `Post`) and a name equal to a client export (`CerialClient`, `CerialId`) are
  refused at generate.
- **Breaking.** In a TypeScript schema, literal values must match their kind,
  and a mismatch is refused when the schema loads. An `int` must be a safe integer,
  so `variant.int(1e21)` is refused; use a `float` or a string variant.
- **Breaking.** Record id types on object fields, the `Record(...)` parameters,
  are validated like a model's. A type that is not a known primitive, tuple or object is now an error
  at generate.
- **Breaking.** The generate output cleanup deletes only the files listed in the output's
  `.cerial-output.json`, with `--clean` too, and only after the new files are
  copied. It refuses to overwrite an existing file it did not write, and refuses
  an output outside the project root or one that contains schema sources. Files
  you added to the output folder are kept. The first run over an output from
  0.2.0 has no manifest and removes nothing, so delete old leftovers by hand
  once.

  ```bash
  # refused: the output holds the schema sources, or lies outside the project
  bunx cerial generate -s ./schemas -o ./schemas
  bunx cerial generate -s ./schemas -o ../shared/db-client

  # fine: an output folder of its own
  bunx cerial generate -s ./schemas -o ./src/db

  # when the location is on purpose
  bunx cerial generate -s ./schemas -o ../shared/db-client --allow-unsafe-output
  ```

  `--allow-unsafe-output` lifts the location refusals; it is new in this release.
- `cerial convert` converts a schema source that lies outside the entry root
  beside itself, under the same exists, `--force` and protected-source checks,
  and writes nothing outside the planned outputs. An export name in a kept
  module that cannot be imported safely is refused.
- **Breaking.** Schema names are validated: a folder, marker or config-key name
  must be a letter followed by letters, digits, hyphens and underscores (`a b`,
  `$x` and `1db` are refused), and two names that give the same client class
  are refused. Hyphenated config keys such as `user-db` are accepted, as the
  docs always said. A folder config used as the root now honours its `name`, so
  that schema's client class changes with it (`AlphaCerialClient` to
  `AuthCerialClient`).
- `cerial init` writes a per-schema `output` in a multi-schema config, and a
  folder name that is not a valid schema name gets a derived one (`default`
  becomes `default_`, `user-db` becomes `user_db`) which `init` reports. The
  config holds names and paths as quoted data.
- **Breaking.** Nested writes inside a nested create, and any relation value
  or unsupported operation on a relation field, are refused with an error
  naming the path, where they used to be dropped without a word.

  ```ts
  // refused: 'posts[0].author' holds a relation value, nothing is written
  await client.db.User.create({
    data: {
      name: 'Ada',
      posts: { create: [{ title: 'Hi', author: { connect: userId } }] },
    },
  });

  // do this instead: one level per call
  const user = await client.db.User.create({ data: { name: 'Ada' } });
  await client.db.Post.create({ data: { title: 'Hi', author: { connect: user.id } } });
  ```
- The exported builders (`buildFindManyQuery`, `buildCreateQuery` and the
  others) and filter handlers validate their input before building. Input the
  client methods already refused is now refused here too.
- The exported where helpers (`transformWhere`, `transformWhereClause` and
  `buildConditions`) refuse a `where` key that names no field, with `CerialUnknownFieldError`, instead of
  leaving it out of the filter.
  A `where` that has keys but resolves to no conditions is refused with a
  `CerialValidationError`; `{}` and `undefined` still give empty text.
  Without a model registry, a relation filter is refused with a
  `CerialValidationError` saying the registry is required.
- An empty OR branch now makes the OR match every row, as `{}` does on its own,
  so `NOT` around it matches none. Filters that relied on the branch being
  dropped return different rows. A relation filter whose only remaining OR
  branch named an unknown field is now refused rather than run.
- An empty filter body is read for what it says: `some: {}` means at least one
  element or related record, `none: {}` means none, `every: {}` holds for any
  array and, on a relation, means at least one related record, as `every`
  already requires there. An empty operator object such as `age: {}` adds no
  condition.
- A nested relation filter follows the relation at every depth, including
  many-to-many relations, which had no working form before. `every` on a
  many-to-many relation requires at least one linked record.
- A reverse relation compared to `null` is refused; use `isEmpty: true`.
- A where must be an object: `[]`, numbers, booleans and `null` are refused on
  every method that takes a where, and on the exported where helpers.
  Leaving where out still means every row.
- Bulk writes (`deleteMany` and `updateMany`) select the matching records first
  and then write exactly those, in a transaction. Results are unchanged except where the
  old single statement saw its own writes.
- A filter on a to-one relation matches only rows whose related record
  exists. Rows with no related record, or one that was deleted, no longer
  match a negative operator such as `neq` or `notIn`; `NOT` around the filter
  includes them. `relation: null` matches rows that have no related record
  (unset, `null`, or a deleted record) and `NOT: { relation: null }` rows that
  have one; on a read `relation: {}` means the same as the latter. For the
  stored key use the foreign key field: `fkField: null` matches a stored `null`
  and `isNone` an unset key. Writes (`deleteMany`, `updateMany`, `upsert`, the
  unique write methods and the exported where helpers) refuse `relation: {}`,
  bodies equivalent to it and an empty operator object such as `age: {}`, and
  name the explicit forms; `some: {}` and `isEmpty` stay allowed.
- Object fields in a relation filter compile by sub-field: an object field, an
  array of objects or a tuple field inside `some`, `every`, `none` or a to-one
  relation filter matches on the sub-fields you name, at any depth and under
  `AND`, `OR` and `NOT`. Filters that relied on the whole-value comparison return
  different rows. To match a whole object, name each sub-field:
  `posts: { some: { meta: { source: 'web', rank: 1 } } }`.
- A tuple index key in a filter must be all digits with no leading zero.
  `'1'` still works; `'01'`, `'1e0'`, `'1 anything'` and a key holding a newline
  are refused as unknown fields. Use the element name or the plain index:
  `coords: { 1: 5 }` or `coords: { lng: 5 }`.
- An empty NOT beside a real condition is refused on writes (`deleteMany`,
  `updateMany`, `deleteUnique`, `updateUnique`, the update half of `upsert`,
  nested update and delete, and the exported where helpers when used for
  writes), at every position in the `where`. That covers `NOT: {}` and a `NOT`
  whose fields are all `undefined`, such as `NOT: { name: body.name }` when the
  request left `name` out. Reads keep their meaning, where `NOT: {}` matches no
  rows. Write the condition you mean, or drop the `NOT`. `NOT: { OR: [] }` is
  still allowed and matches every row.
- A lost operator under an undeclared `@flexible` sub-key is refused on writes,
  the same as on a declared field. `address: { extra: { eq: body.extra } }` with
  `extra` left out of the request used to be dropped, so
  `deleteMany({ where: { name: { neq: 'zz' }, address: { extra: { eq: body.extra } } } })`
  removed every row not named `zz`. It now throws and changes nothing. A value
  comparison on such a key still runs: `extra: 'x'`, `extra: {}` and
  `extra: { foo: 1 }`. Reads are unchanged.
- The txn option of a model method must be a transaction from `$transaction`, or
  left out. Any other value, `null` included, is refused with a
  `CerialValidationError` naming `txn` before the query runs.
- Query placeholders, the internal bound-variable names, changed, and
  transaction items run without their text being rewritten. Query results are unchanged. Code that matched on
  generated variable names in compiled statements must stop doing so.
- An unknown operator, or an `AND`, `OR`, `NOT`, `some`, `every` or `none` body
  of the wrong shape, is refused at every depth of a `where` with a
  `CerialValidationError` naming the path. `OR` and `AND` take an array of
  objects, `NOT`, `some`, `every` and `none` take an object. A filter on a
  relation takes an object as well. Filters that carried an unknown operator
  and relied on its being dropped now throw: remove the operator, or correct
  its name.
- Nested creates are validated like a top-level `create`. Required fields,
  types and unknown keys in the nested record are refused with the field named,
  where 0.2.0 coerced them. The foreign key a reverse nested create receives
  from its parent does not need to be passed.
- `push`, `set` and `unset` on a primitive array refuse a value that is not the
  element type, naming its position. Pass numbers to `Int[]` and `Float[]`,
  strings to `String[]`, and so on, as you would to `create`.
- Decimal values must be a finite number, a `CerialDecimal`, or a
  decimal string read in full: digits with an optional `-`, a fraction and an exponent,
  such as `'12.50'`, `'-3'` or `'1e3'`. A string with a space, a thousands
  separator or comma, a trailing letter or a leading `+` is refused, and so are
  `NaN` and `Infinity`, in data, in a filter and in `new CerialDecimal(...)`.
  Strip the `+` and whitespace, and use `.` as the separator, before passing the
  value.
- The exported builders, `compile*` functions and `QueryBuilder` refuse a
  relation filter or a nested relation operation when no model registry is
  passed. Pass the registry as the last argument, as the client does.
- `findUnique` by id applies relation filters in the same `where`, so a row the
  filter excludes now returns `null`.
- An `undefined` unique key is refused by name on `findUnique`, `updateUnique`,
  `deleteUnique` and `upsert`. Leave the
  key out of the `where`, or check the value first:
  `where: body.email ? { email: body.email } : { id }`.
- Model methods refuse an option key they do not take, with a
  `CerialValidationError` naming the key and listing the accepted ones. `txn`
  stays accepted everywhere. Code that passed an extra key and relied on its
  being ignored must remove it.
- `updateWhere` and `unset` on an array of objects throw instead of doing
  nothing. Replace the whole array, with the array itself or `{ set }`, or add
  elements with `{ push }`.
- Object array operators: on an array of objects only the whole array, `{ set }`
  and `{ push }` are accepted. `pop`, `remove`, `delete` and the object form of `unset`
  (`unset: { items: { qty: true } }`) used to be accepted and changed nothing;
  they now throw a `CerialValidationError` naming the field and the supported
  forms, before any query.
- **Breaking.** upsert is single-row. Whatever its `where` matches, such as a
  null on a nullable unique key, non-unique keys such as `{ name: 'shared' }`
  or an object `@unique` key beside other keys, it updates the first matching
  row and no other, with or without relation operations, and in every
  `$transaction` mode. A non-unique `upsert` in 0.2.0 updated every matching
  row and returned them all; it now returns an array holding the one updated
  row. A `null` on a `nullsNotDistinct` unique key names at most one row, so
  it updates that row when it exists and creates one otherwise. To change
  several rows, use `updateMany`.
- The option keys on the builders are checked too: the check also runs on the exported `compile*` functions and on
  every `QueryBuilder` and `QueryBuilderStatic` method that takes options, so
  `compileDeleteMany(model, { wehre })` throws. The options of an `include`
  accept `select`, `where`, `orderBy`, `limit`, `offset` and `include`; any
  other key throws a `CerialValidationError` naming it instead of including
  every related row.

- **Breaking.** Flexible key default: migrating a new key with a `@default` under a
  `@flexible` object field is now a data-loss step. If you ran `cerial migrate apply --from-schema`
  with no flags for such a change, add `--allow-data-loss` as well as
  `--allow-destructive`, or review the plan file and uncomment the step. Stored
  values that convert to the field type are kept.
- Removing `@flexible` from an object field on a table with rows cannot be applied by `cerial migrate` yet: the plan classes it as data loss, and with both flags the apply fails and rolls back with every row unchanged. Keep `@flexible` on the field, or apply the change while the table is empty (export, apply, import).
- **Breaking.** Several schema folders: with no config and no `-s`, discovery
  refuses when more than one `schemas/` or `schema/` folder holds schema files. It lists them. Add a
  `cerial.config.ts` (`cerial init` writes one) or pass `-s <path>`. Discovery
  starts at the folder you run `cerial` from and never reads `node_modules`, a
  parent folder or a sibling folder. A schema you kept in one of those, or in a
  symlink that leaves the project, needs `-s` or a config `path`.
- **Breaking.** Writes outside the project root: `cerial format` and `cerial convert` (with `--remove-source`,
  `--partial` and the files they stage) refuse to write or delete a file whose
  real path is outside the project root, even one `-s` or the config names. The
  refusal prints the path. Run the command from a folder that contains the files.
- The CLI pages now say what each command imports and runs. `generate`, `migrate`
  and `convert` import the project's TypeScript schema modules and its
  `cerial.config.ts`, `format` runs only the config, and `init` runs none of it.
  With no config, every `*.schema.ts` under the project root is a schema module.
  Read a checkout before you run `cerial` in it.

### Removed

- `generateMigrationCode` is no longer exported. Nothing in Cerial called it, it
  duplicated `generateMigrationQuery` without escaping its output, and the
  escaping work above would have had to be done twice to keep it. Use
  `generateMigrationQuery` from `cerial/generators`, which takes the same
  arguments and quotes what it emits.
- **Breaking.** `escapeIdent` and `escapeIdPart` are no longer exported from the
  package root. They were re-exports of SDK functions that do not escape a
  backslash, so a value could end the quoted identifier early and inject a
  statement (see Security). Use `sql.ident` for an identifier and bind values
  as parameters. If you still need the SDK's own functions, import them from
  `surrealdb` and do not pass them untrusted input.
- `validateSchema` is no longer exported from the package root or from `cerial/parser`.
  That export was a second copy of the schema validator that returned `ParseError[]` and
  that nothing in `cerial generate` ever called, so roughly forty-five of its checks
  never ran against a real schema. The checks now run on the path `cerial generate` uses.
  If you called the exported copy directly, use the CLI schema validator, which returns
  `{ valid, errors }`.
- **Breaking.** The code generation and CLI runtime exports are no longer exported
  from the package root, so importing `cerial` no longer loads the formatter or the
  generators. Each name still exists on the subpath that already held it, so an
  import that no longer resolves needs only a new module specifier.
