Cerial automatically generates migration statements from your schema and runs them against SurrealDB. Migrations ensure your database structure matches your `.cerial` definitions.

## What Migrations Do

Migrations execute SurrealQL statements that define the structure of your database:

- **`DEFINE TABLE`** creates tables with `SCHEMAFULL` enforcement (only defined fields are allowed)
- **`DEFINE FIELD`** defines fields with types, defaults, and constraints
- **`DEFINE INDEX`** creates indexes for [`@unique`](/schema/decorators/unique) fields

These statements are idempotent. Running them multiple times has the same effect as running them once. Cerial emits every `DEFINE` with `OVERWRITE`, which replaces an existing definition of the same name, so migrations are safe to re-run. `OVERWRITE` only replaces what the statement names. `DEFINE TABLE OVERWRITE` leaves the table's existing fields and indexes in place, and no emitted statement ever removes a field, index or table that your schema no longer mentions (see [Removing a field](#schema-changes)). Measured on SurrealDB 3.3.0.

## Lazy Migration (Default)

By default, migrations run automatically before the first query. Just connect and start querying:

```typescript
import { CerialClient } from './db-client';

const client = new CerialClient();

await client.connect({
  url: 'http://localhost:8000',
  namespace: 'main',
  database: 'main',
  auth: { username: 'root', password: 'root' },
});

// First query triggers automatic migration
const users = await client.db.User.findMany();
// ^ Migrations ran before this query executed
```

This is convenient for development and simple applications. The first query takes slightly longer due to migration overhead, but subsequent queries run at full speed.

## Explicit Migration

If you want to control exactly when migrations run, call `migrate()` directly:

```typescript
const client = new CerialClient();

await client.connect({
  url: 'http://localhost:8000',
  namespace: 'main',
  database: 'main',
  auth: { username: 'root', password: 'root' },
});

// Run migrations explicitly
await client.migrate();

// Now query, no migration overhead on first query
const users = await client.db.User.findMany();
```

Explicit migration is useful when:

- You want predictable startup timing (e.g., health checks that pass only after migration)
- You're running migrations as a separate step in a deployment pipeline
- You want to catch migration errors early, before any queries run

## Migration Status

Migration status is tracked per model. Once a model's migration has run (either lazily or explicitly), it won't run again on that client. `migrate()` covers every model, and a lazy migration covers only the model you query:

```typescript
await client.connect({ ... });

// First call: runs migrations
await client.migrate();

// Second call: no-op, migrations already ran
await client.migrate();

// Queries: no migration overhead
await client.db.User.findMany();
await client.db.Post.findMany();
```

If you disconnect and reconnect, migrations will run again on the next query or `migrate()` call.

:::caution
The migration modes, change classes and state tables below are not yet available in the current release. They will ship in an upcoming version.
:::

## Migration Modes

The `migrations` client option sets how a client treats the schema. It takes `'auto'`, `'verify'` or `'off'`.

| Mode | On connect and first use | `migrate()` |
|---|---|---|
| `'auto'` (default) | Applies a model's definitions the first time it is used | Applies every model |
| `'verify'` | Compares the live schema with the generated one and applies nothing | Applies every model |
| `'off'` | Applies nothing, checks nothing, and reads or writes no migration state | Applies every model |

`'auto'` is the default through 0.x, so existing applications behave as before. Under `NODE_ENV=production` it logs a one-time warning that it applies schema changes on first use, and it logs the plan before it changes a schema that differs from the generated one. `resetMigrationState()` makes an `'auto'` client apply every model again on next use.

**Use `'verify'` in production.** Migrate in a deploy step (`cerial migrate apply`, or `client.migrate()` from a release script), and let the running application only check:

```typescript
const client = new CerialClient({ migrations: 'verify' });

await client.connect({
  url: process.env.DB_URL!,
  namespace: 'main',
  database: 'main',
  auth: { username: process.env.DB_USER!, password: process.env.DB_PASSWORD! },
});
```

If the database does not match the generated schema, `connect()` throws a [`CerialMigrationError`](/errors) naming each construct that differs, and the client stays disconnected. The error's `plan` holds what would bring the database to the generated schema. Nothing was applied. Events, functions and tables Cerial did not create are ignored, so a database you share with other tools still verifies.

`'off'` is for a database whose schema something else owns. The client sends no definitions and no state queries on any query, `$raw`, `$live` or `$transaction` call. An explicit `migrate()` still runs:

```typescript
const client = new CerialClient({ migrations: 'off' });

await client.connect({ url: 'http://localhost:8000', namespace: 'main', database: 'main' });

// The schema is not touched until you ask
await client.migrate();
```

`'auto'` needs no configuration. To set it explicitly:

```typescript
const client = new CerialClient({ migrations: 'auto' });
```

For deploys that review changes before they run, use the [`cerial migrate`](/cli/migrate) command.

## Classes of Change

Every difference between the generated schema and the database belongs to one class. The class decides what [`cerial migrate apply`](/cli/migrate#what-needs-approval) asks for, and each line of a `'verify'` refusal and an `'auto'` warning is labelled with it.

| Class | Meaning | Schema change that causes it |
|---|---|---|
| `additive` | Adds a structure and cannot affect existing rows | A new `phone String?` field on `User`, a new model, a new `@unique` |
| `destructive` | Drops a structure, or can leave existing rows unable to be written | Removing `nickname` from `User`, changing `age Int` to `age String`, adding a required `String` field with no default |
| `data-loss` | Destroys rows with no separate step | Deleting `model Post` from the schema |
| `unmanaged` | Something Cerial has no concept for, or did not create | An event or function you defined by hand, a table the schema never declared |

An unmanaged item is reported and never changed, and it never fails `'verify'`. A table is only proposed for removal when Cerial created it.

Cerial does not detect renames. Renaming `nickname` to `handle` is a destructive removal plus an additive new field, and the stored values are not carried across.

## Rolling Back

There are no `down` migrations and no command that undoes an applied change. Your schema is declarative, so the way forward is always derived from the schema, and a generated inverse would be a guess about data that may no longer exist.

To roll back, restore the database from a backup, then fix forward: change the schema, regenerate, and migrate again. Take a backup before any destructive or data-loss change.

## Atomicity

A failed apply rolls back as a unit on the memory backend of SurrealDB 3.3.0, which is the only backend this behaviour has been measured on. Other backends have not been measured, so atomicity is not promised for them. After a failed apply, check the database with `cerial migrate status` before retrying.

## Migration State

Cerial records what it has applied in two tables in your own database:

- `_cerial_migrations` holds one row per model and a row for the schema as a whole, so a later client can skip definitions that are already applied.
- `_cerial_migration_lease` holds a single record that stops two migrations running against one database at the same time.

Cerial defines both tables itself, so the connected user needs the right to define tables. Do not edit, delete or write to them. A changed row makes Cerial believe the database is in a different state than it is, which can skip a needed change or reapply one. Back them up with the rest of the database. If the state is lost, `cerial migrate baseline` records the live schema again.

## Generated Migration Statements

The migration generator produces SurrealQL statements based on your schema. Here's what gets generated for different schema constructs.

### Table Definitions

Every `model` in your schema generates a `DEFINE TABLE` statement:

```sql
DEFINE TABLE OVERWRITE user SCHEMAFULL;
DEFINE TABLE OVERWRITE post SCHEMAFULL;
DEFINE TABLE OVERWRITE tag SCHEMAFULL;
```

The `SCHEMAFULL` option means SurrealDB rejects any fields not explicitly defined. This provides strict schema enforcement.

### Field Definitions

Each field generates a `DEFINE FIELD` statement with the appropriate SurrealQL type:

```sql
-- String field (required)
DEFINE FIELD OVERWRITE name ON TABLE user TYPE string;

-- Optional field (accepts NONE)
DEFINE FIELD OVERWRITE bio ON TABLE user TYPE option<string>;

-- Optional and @nullable field (accepts NONE and null)
DEFINE FIELD OVERWRITE nickname ON TABLE user TYPE option<string | null>;

-- Boolean with default
DEFINE FIELD OVERWRITE isActive ON TABLE user TYPE bool DEFAULT true;

-- DateTime with @createdAt (set on creation when absent)
DEFINE FIELD OVERWRITE createdAt ON TABLE user TYPE option<datetime> DEFAULT time::now();

-- DateTime with @updatedAt (set on creation and re-set on every update)
DEFINE FIELD OVERWRITE updatedAt ON TABLE user TYPE option<datetime> DEFAULT ALWAYS time::now();

-- DateTime with @now (computed, not stored)
DEFINE FIELD OVERWRITE currentTime ON TABLE user TYPE datetime COMPUTED time::now();

-- Integer field
DEFINE FIELD OVERWRITE age ON TABLE user TYPE option<int>;

-- Float field
DEFINE FIELD OVERWRITE score ON TABLE user TYPE option<float>;
```

See [`@default`](/schema/decorators/default), [`@createdAt`](/schema/decorators/created-at), [`@updatedAt`](/schema/decorators/updated-at), and [`@now`](/schema/decorators/now) for details on each decorator.

### Record Fields

`Record` fields generate `record<tablename>` types that enforce referential integrity at the database level:

```sql
-- Required record reference
DEFINE FIELD OVERWRITE authorId ON TABLE post TYPE record<user>;

-- Optional record reference
DEFINE FIELD OVERWRITE reviewerId ON TABLE post TYPE option<record<user>>;

-- Array of record references (duplicates are dropped, absent becomes [])
DEFINE FIELD OVERWRITE tagIds ON TABLE post TYPE array<record<tag>> VALUE IF $value THEN $value.distinct() ELSE [] END;
```

Array fields default to an empty array, so they are not `option<...>`.

### Embedded Object Fields

[Object](/objects) fields generate nested `DEFINE FIELD` statements using dot notation:

```sql
-- Object field
DEFINE FIELD OVERWRITE address ON TABLE user TYPE object;
DEFINE FIELD OVERWRITE address.street ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE address.city ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE address.state ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE address.zipCode ON TABLE user TYPE option<string>;

-- Optional object field
DEFINE FIELD OVERWRITE shipping ON TABLE user TYPE option<object>;
DEFINE FIELD OVERWRITE shipping.street ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE shipping.city ON TABLE user TYPE string;

-- Array of objects
DEFINE FIELD OVERWRITE locations ON TABLE user TYPE array<object>;
DEFINE FIELD OVERWRITE locations.*.lat ON TABLE user TYPE float;
DEFINE FIELD OVERWRITE locations.*.lng ON TABLE user TYPE float;
```

### Index Definitions

Fields with the [`@unique`](/schema/decorators/unique) decorator generate unique index statements:

```sql
DEFINE INDEX OVERWRITE user_email_unique ON TABLE user COLUMNS email UNIQUE;
DEFINE INDEX OVERWRITE tag_name_unique ON TABLE tag COLUMNS name UNIQUE;
```

### Tuple Fields

[Tuple](/tuples) fields generate a `DEFINE FIELD` with a typed array literal that enforces element types, count, and optionality:

```sql
-- Required tuple: [float, float]
DEFINE FIELD OVERWRITE location ON TABLE user TYPE [float, float];

-- Optional tuple: option<[float, float]>
DEFINE FIELD OVERWRITE backup ON TABLE user TYPE option<[float, float]>;

-- Tuple with a @nullable element: [float, float | null]
DEFINE FIELD OVERWRITE coords ON TABLE user TYPE [float, float | null];

-- Array of tuples: array<[float, float]>
DEFINE FIELD OVERWRITE history ON TABLE user TYPE array<[float, float]>;
```

**Sub-field constraints** are only emitted for tuple elements that need them: elements with decorators ([`@default`](/schema/decorators/default), `@defaultAlways`, [`@createdAt`](/schema/decorators/created-at), [`@updatedAt`](/schema/decorators/updated-at)) and object or nested-tuple elements:

```sql
-- Element with @default
DEFINE FIELD OVERWRITE data[0] ON TABLE user TYPE string DEFAULT 'hello';

-- Object element with sub-fields
DEFINE FIELD OVERWRITE data[2] ON TABLE user TYPE object;
DEFINE FIELD OVERWRITE data[2].name ON TABLE user TYPE string;
```

Plain primitive elements (with no decorators, including `@nullable` ones, whose `| null` lives in the tuple's type literal) do **not** get sub-field `DEFINE FIELD` statements. The parent tuple type literal already enforces their types. This is intentional, to avoid a [known SurrealDB issue](#known-limitation-tuple--object-interaction) where sub-field constraints on tuple elements can cause incorrect initialization.

### ID Fields

The `id` field with `@id` decorator is **not** included in migrations. SurrealDB automatically manages the `id` field for every table.

## Complete Example

Given this schema:

```cerial
object Address {
  street String
  city String
  state String
  zipCode String?
}

model User {
  id Record @id
  name String
  email String @unique
  bio String?
  age Int?
  isActive Bool @default(true)
  createdAt Date @createdAt
  address Address
  posts Relation[] @field(postIds)
  postIds Record[]
}

model Post {
  id Record @id
  title String
  content String?
  publishedAt Date?
  author Relation @field(authorId)
  authorId Record
}
```

The generated migrations:

```sql
-- User table
DEFINE TABLE OVERWRITE user SCHEMAFULL;
DEFINE FIELD OVERWRITE name ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE email ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE bio ON TABLE user TYPE option<string>;
DEFINE FIELD OVERWRITE age ON TABLE user TYPE option<int>;
DEFINE FIELD OVERWRITE isActive ON TABLE user TYPE bool DEFAULT true;
DEFINE FIELD OVERWRITE createdAt ON TABLE user TYPE option<datetime> DEFAULT time::now();
DEFINE FIELD OVERWRITE address ON TABLE user TYPE object;
DEFINE FIELD OVERWRITE address.street ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE address.city ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE address.state ON TABLE user TYPE string;
DEFINE FIELD OVERWRITE address.zipCode ON TABLE user TYPE option<string>;
DEFINE FIELD OVERWRITE postIds ON TABLE user TYPE array<record<post>> VALUE IF $value THEN $value.distinct() ELSE [] END;
DEFINE INDEX OVERWRITE user_email_unique ON TABLE user COLUMNS email UNIQUE;

-- Post table
DEFINE TABLE OVERWRITE post SCHEMAFULL;
DEFINE FIELD OVERWRITE title ON TABLE post TYPE string;
DEFINE FIELD OVERWRITE content ON TABLE post TYPE option<string>;
DEFINE FIELD OVERWRITE publishedAt ON TABLE post TYPE option<datetime>;
DEFINE FIELD OVERWRITE authorId ON TABLE post TYPE record<user>;
```

## Schema Changes

When you modify your schema and regenerate the client, the migration statements are regenerated. Since SurrealDB's `DEFINE` statements are idempotent (create-or-replace), re-running migrations applies the new schema.

**Adding a field:**

```cerial
model User {
  // ...existing fields...
  phone String?   // ← New field
}
```

Regenerate and the new `DEFINE FIELD OVERWRITE phone ON TABLE user TYPE option<string | null>` statement is included. Existing records have `NONE` for the new field until updated. A required field with no default has no value to give existing rows, so their next write to the row is refused until they hold one.

:::warning
**Removing a field** from the schema removes its `DEFINE FIELD` statement from the generated migrations, but the client's migrations never emit `REMOVE FIELD`. The field **keeps both its definition and its data** in SurrealDB, and `SELECT *` still returns it. Re-running migrations does not change this, and `DEFINE TABLE OVERWRITE` does not remove fields from a table either.

If you drop the definition yourself with `REMOVE FIELD <name> ON TABLE <table>;`, the stored values stay on every row that held one, and **every later write to such a row fails** (`Found field '<name>', but no such field exists`) until the value is unset. Reads are unaffected and nothing is lost, but the row cannot be updated. Remove the definition and unset the values together, in this order, in one transaction:

```sql
BEGIN;
REMOVE FIELD <name> ON TABLE <table>;
UPDATE <table> UNSET <name>;
COMMIT;
```

Unsetting first and removing the definition second fails with a coercion error and rolls the whole transaction back. To remove a single child of an object field, unset the child path (`UNSET <parent>.<child>`); the row keeps an empty parent object.
:::

**Changing a field type:**

Changing a field type regenerates the `DEFINE FIELD` with the new type. SurrealDB 3.3.0 accepts the new definition over existing rows and leaves their values untouched, so reads still return the old value. The next write that touches such a row fails with `Couldn't coerce value for field` until that row holds a value of the new type. Setting the field to a valid value repairs the row.

## Known Limitation: Tuple + Object Interaction

SurrealDB has a bug where optional tuple fields with sub-field constraints (`DEFINE FIELD field[N]`) can be incorrectly initialized as `{}` (empty object) instead of NONE when:

1. The model has an optional tuple field with per-element `DEFINE FIELD` sub-field constraints
2. The model also has an optional object field with its own sub-field constraints

Cerial mitigates this by skipping sub-field `DEFINE FIELD` statements for primitive tuple elements that don't need them (no decorators). The parent tuple type literal already enforces element types, so the sub-field constraints are redundant for plain primitives.

For models that combine optional tuples with required-decorated elements (which _need_ sub-field constraints) and optional object fields, Cerial's schema validator reports an error at generation time. This prevents deploying a schema that would trigger the bug.
